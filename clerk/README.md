# clerk

The clerk (*le greffier*, [ticket #265](https://github.com/linagora/twalk/issues/265)): the Twalk component that writes onto the owner's own Buzz relay what the bus says, and — since [#284](https://github.com/linagora/twalk/issues/284) — carries what the owner decides there to the Companion Gateway, **as a device of the owner**. Buzz is a **surface and never an authority** ([ADR 0032](../docs/architecture/adr/0032-twalk-governs-what-an-agent-outside-it-may-see-and-do.md)): the clerk holds no consent snapshot, no store, no key of Hermes's, and no credential the Companion Gateway would take for anyone but the owner's own device — not the service token that opens the consent snapshot, and no device token at rest beyond the fifteen minutes one lives in memory. Its secrets are a Nostr key of its own and, for the write half, one refresh token in a file it owns and rotates ([ADR 0036](../docs/architecture/adr/0036-the-clerk-approves-as-a-device-of-the-owner.md)).

Three durable consumers read the bus and turn what they read into a post in one of three channels an operator's `provision-buzz-channels.sh` created for it. A fourth loop, the sweep, deletes a post once its suggestion expires. A fifth, the **decisions** loop, reads the gestures on the clerk's own posts and carries the owner's ✅ to `POST /api/approvals` — the Companion Gateway's, which remains the single writer of that decision ([ADR 0022](../docs/architecture/adr/0022-the-approval-api-lives-on-the-companion-gateway.md)). Buzz decides nothing.

## The three channels: what each carries, and what it never does

| Channel | Fed by | Carries | Never carries |
| --- | --- | --- | --- |
| `approbations` (`CLERK_CHANNEL_APPROVALS`) | `persona.suggest.produced` | One forum post per suggestion: the suggestion's body verbatim, the clerk's own sentences (network, expiry, and the gesture line — `✅ send as is · ❌ decline · reply here to send a different text`), and a reference line last (`twalk:suggestion:<id> expires <rfc3339>`). In its thread, the clerk's answer to a gesture: a Gateway refusal in the Companion's own words, or "only the owner approves" | A display name, an excerpt, a `network_identifier`, a room id — the approval screen cannot name the contact ([#160](https://github.com/linagora/twalk/issues/160)) and this surface cannot either ([ADR 0012](../docs/architecture/adr/0012-revoked-consent-reduces-publication.md)). A thread answer carries the sentence for a code and nothing of the message |
| `journal` (`CLERK_CHANNEL_JOURNAL`) | `persona.reply.approved.v1.posted` | One stream line per posted reply: which network, which Matrix ID it was posted as, its `reach` (`contact`, visibly not `nobody`), whether it was edited, the approval's id, and the time | Any text of the reply — so "nothing Twalk writes onto Buzz quotes a contact" holds without an exception to defend |
| `activite` (`CLERK_CHANNEL_ACTIVITY`) | `bridge.status.changed`, `consent.state.changed`, and the clerk's own posts, decisions and sweep | Only what calls for a look: a bridge down and back, a consent decision (by the *kind* of subject and the new state and networks), a suggestion produced, a suggestion approved from Buzz (edited or as proposed, on which network), one declined from Buzz with ❌, a suggestion that expired undecided and was deleted | `persona.thinking.emitted`, a message count, a sender identity, or the owner's own reply text — on Buzz, a channel that chatters is a channel that gets muted |

A consent line names the kind of subject (contact, network, persona) and never the subject's Matrix ID — the same rule the Companion's dashboard activity feed follows (`companion/src/lib/dashboard/model.ts`).

The clerk's own sentences exist in French and English (`CLERK_USER_LANGUAGE`); a suggestion's body is posted exactly as the event carried it, whatever language that is.

## Three decisions worth arguing with

**Its own Nostr key.** Not Hermes's — the reader must know who speaks, and what Twalk decided about consent and delivery is not Hermes's to say — and not the Companion Gateway's, because ADR 0032 refuses a Nostr private key in the Gateway. `provision-nostr-key.sh` generates it; the owner tells the relay to accept it and adds it to each channel with `provision-buzz-channels.sh --bot <hex>`.

**No state of its own** ([ADR 0035](../docs/architecture/adr/0035-the-clerk-is-a-projection-of-the-relay-and-holds-no-state.md)). What it already wrote, it finds on the relay — never in a store — and the mechanism is per channel. A **forum post** in `approbations` is recognised by its reference line, `twalk:suggestion:<id> …`, read off the clerk's own posts. A **stream message** in `journal` or `activite` is recognised by a tag every one of them carries, `["r", "twalk:event:<the bus event's id>"]`, which the clerk queries (`#r`) before writing a journal line or a consent or bridge line (the two `activite` lines that follow a forum post rest on that post's own key); the simpler mechanism — dating the line from the bus event's `time` so a redelivery hashed to the same Nostr id and the relay's own duplicate answer did the work — was tried first and does not survive contact with Buzz, which refuses any `created_at` more than fifteen minutes from its clock, and a redelivery after a relay outage is exactly that old. Either way a redelivery of a trigger already handled (a SIGTERM between the relay's `2xx` and the ack, a lost ack, an `ACK_WAIT` overrun) and a cold restart are answered by the same query with the same result, counted as `twalk_clerk_skipped_total{why="duplicate"}`. A SQLite of suggestion id → post id was weighed and rejected: it would make the relay a copy of something Twalk holds, and the moment the two disagreed — a post deleted from Buzz Desktop, a relay restored from an older backup — nothing would say which was true.

**The sweep** (`CLERK_SWEEP_SECONDS`, a minute by default). Every tick it rereads its own posts in `approbations`, deletes each one whose reference line names an `expires_at` that has passed, and says so once in `activite` ([#219](https://github.com/linagora/twalk/issues/219)) — so the relay never holds a quoted word longer than the suggestion that carried it lived, well inside [ADR 0028](../docs/architecture/adr/0028-a-contacts-words-live-apart-from-the-event-that-identifies-them.md)'s seven days. A post it **cannot date** — the contract makes `expires_at` optional and a third-party persona need not set it; an expiry that does not parse; a reference line it does not recognise — is not the one exception that stays for ever: it goes once the relay's own `created_at` on it is seven days old, counted apart as `twalk_clerk_deleted_total{why="undatable"}`, and every sweep that read one warns how many it could not date, so a channel quietly accumulating them is visible before the week is out. Deletion on a *decision* — the owner approving a suggestion, editing and sending it, or refusing it — is the decisions loop's ([#284](https://github.com/linagora/twalk/issues/284), below), because deciding is; the sweep's deletion only ever follows a clock.

## The write half: a ✅ is the approval ([#284](https://github.com/linagora/twalk/issues/284))

`approbations` is a forum, so a suggestion is a post with a thread, and the gestures on it are the decision. The rules are few and closed:

| The owner's gesture on a post | What the clerk does |
| --- | --- |
| A **✅** reaction (`✅` or `✔️`) | Approves the suggestion **as written**: `POST /api/approvals` with the suggestion's id and no `final`. On success the post is deleted (after a decision the text has done its job, [#219](https://github.com/linagora/twalk/issues/219)) and `activite` says "approved from Buzz"; `journal` gets its line when the Sensor's `.posted` report arrives. |
| A **reply in the thread** (a direct reply, with text) | Approves it **with that text** — the edit the approval screen allows ([#100](https://github.com/linagora/twalk/issues/100)): `final.body` is the reply, the approval's `edited` is true. The post is deleted; the owner's own reply stays, theirs ([ADR 0028](../docs/architecture/adr/0028-a-contacts-words-live-apart-from-the-event-that-identifies-them.md)), now without a root. |
| A **❌** reaction (`❌` or `✖️`) | The Companion's *Refuser*, local by nature: the post is deleted, `activite` says "declined from Buzz (not forwarded)", and nothing reaches the Companion Gateway. |
| Anything else — another emoji, a nested reply, an empty reply | Not a decision. No vote (a ranking is not a decision) and no magic word ("oui" under "on dit 20h ?" is ambiguous). |

**Who may.** The owner's key **alone**, from configuration (`CLERK_OWNER_PUBKEY`) and never read off the relay: a compromised relay must not be able to name a second approver, and a relay `admin` is not the owner. And the key's **signature**, not the relay's word: every event a `/query` answers is verified (id and Schnorr signature) before it can be a gesture, a post of the clerk's or an answer of the clerk's, so a relay that serves a stranger's ✅ under the owner's `pubkey` gets nothing sent — the event is dropped, warned about by id and kind, and counted (`twalk_clerk_skipped_total{why="unverified"}`). A gesture by any other key makes **no Gateway call**, is answered once in the thread ("Only the owner approves."), and is counted (`twalk_clerk_approvals_total{outcome="not_the_owner"}`).

**The credential: a device of the owner** ([ADR 0036](../docs/architecture/adr/0036-the-clerk-approves-as-a-device-of-the-owner.md)). The clerk is what a phone or a browser tab is on the Companion Gateway — a device of the owner's session ([#52](https://github.com/linagora/twalk/issues/52)), named `Buzz`, listed on the dashboard and revoked there like any other — and nothing more privileged. The approval it makes is the owner's: the row reads `approved_by: <owner>`, through that device. It holds one **refresh token**, in a file (`CLERK_GATEWAY_SESSION_FILE`) it owns and rewrites on every `POST /api/session/refresh`, because the Gateway rotates both tokens on every refresh and the old one dies at that moment; the file is rotated **before** the new device token is believed, so a clerk killed between the two still holds a live session. The **device token** lives in memory for the fifteen minutes the Gateway grants it and is written nowhere. An operator creates the session once with `deploy/docker-compose/provision-clerk-device.sh` — the owner's Matrix password at the terminal, a Matrix OpenID token, `POST /api/session` — and runs it again when the device is dead: revoked from the dashboard, or its refresh token unused for thirty days (a clerk asleep that long). The script is idempotent, for [#227](https://github.com/linagora/twalk/issues/227)'s reason: a credential nobody knows exists is one nobody revokes, so an alive session is refreshed and kept, and a new one revokes every other unrevoked device named `Buzz`.

Two alternatives were weighed and rejected, and ADR 0036 says why at length. **A second service token** would be a second class of credential on the Gateway — beside the one that opens the consent snapshot — with `approved_by` fixed by configuration rather than by who signed in, and nothing on the dashboard to revoke. **NIP-98 on the Gateway** — the Gateway verifying the owner's Nostr signature on the approval itself — would put a Nostr verifier on the Gateway's write path for the sake of one client, and make the Gateway learn a second identity for the owner beside the Matrix one it already verifies.

**What the clerk does with the answer.** The refusal vocabulary is the Gateway's ([#24](https://github.com/linagora/twalk/issues/24), [#97](https://github.com/linagora/twalk/issues/97), [#100](https://github.com/linagora/twalk/issues/100): "two doors onto one fact must not teach a client two vocabularies"). `consent_revoked`, `suggestion_expired`, `410 suggestion_out_of_reach` and every other code are answered in the thread with **the Companion's own sentence** for that code — cause and next step, embedded from `companion/src/lib/i18n/{fr,en}.json` at build time (`refusals.rs`), in the owner's interface language (`CLERK_USER_LANGUAGE`), never the reply's — prefixed "Not sent —", or "Sent but not recorded —" for the one code where the reply did go out. A thread answer carries that sentence and nothing else: not the message, not the owner's reply text, not the contact. `409 already_approved` is the Gateway's normal answer to a duplicate and is **success**: the post is deleted and nothing is said. A `401` the Gateway gives to a session it will not have — the device revoked, or the refresh token dead — is answered once in the thread naming the dashboard and the script, and the loop stops retrying it, since retrying a revocation would be a hot loop of refusals.

**Recovery.** The reaction *is* the retry: a ✅ already present when the clerk starts is a decision to carry, and one redelivered — the same signed event submitted twice, a second tick, a restart — sends once, because a post the clerk approved is gone and a thread it answered carries the gesture's id in an `r` tag (`twalk:gesture:<event id>`), the same shape as the rest of its memory ([ADR 0035](../docs/architecture/adr/0035-the-clerk-is-a-projection-of-the-relay-and-holds-no-state.md), unchanged: the session file is a credential, not state). A Gateway that does not answer is retried every tick with a warning and a count (`gateway_unreachable`) for the suggestion's remaining lifetime; when that runs out the thread says "not recorded — react again" and the sweep deletes the post.

Other rulings, briefer:

- `CLERK_RELAY_URL` is the URL the relay **announces**, not merely one that reaches it: NIP-98 binds every signed request to an exact URL, and a Buzz relay is multi-tenant by `Host`.
- The decisions loop polls the relay over the same NIP-98 HTTP the clerk already speaks — two `/query` a tick, three when a gesture is pending (the clerk's own posts, the gestures on them, its own answers) — twenty-four to thirty-six of the relay's three hundred a minute at the default `CLERK_DECISION_SECONDS` — rather than holding a WebSocket subscription: a second transport for one client was not worth what it would add.
- An unreachable relay costs a warning, a counter (`twalk_clerk_relay_failures_total`) and a retry with backoff (transient failures are `Nak`ed onto the bus; a refusal of the request itself is logged once and acked, because a post the relay refuses once will refuse the same way again). Neither ever stops the process. The retry is sized to the hour a suggestion lives by default: sixty-four deliveries, two, four, eight, sixteen and thirty-two seconds apart and then a minute, so the last one still finds the suggestion alive and a relay outage shorter than its life loses nothing — and a poisoned message costs at most that hour, since an expired one is skipped on the delivery that finds it so.
- A suggestion that expired before the clerk got to it — including one redelivered after an outage — is skipped and counted (`twalk_clerk_skipped_total{why="expired"}`), never posted stale.
- An owner's ✅ or edited reply on a post whose suggestion expired since the last tick — a decision in its last seconds — is not swept in silence: the thread is told once ("Non envoyée — la suggestion avait expiré."), counted under `suggestion_expired` as the Companion Gateway would have answered, and the sweep then deletes the post; the `activite` line still reads "expired undecided", because nothing was sent.
- No log line and no error carries a body the relay sent: a refusal keeps the relay's own `error`/`message` field cut to 120 characters, and a `2xx` that is not the answer a route gives is described by its parse failure and its length — for `/query` that body is the clerk's own posts, which quote suggestions.
- `CLERK_USER_LANGUAGE` is one of the Companion's five (`en`, `fr`, `it`, `es`, `de`) and anything else refuses to start. Unset is `en` **with a startup warning**: on the reference deployment the personas' language comes from the Companion's settings (#184), which the clerk cannot read — that read takes the service token — so a French deployment gets an English clerk until the operator sets it in `deploy/docker-compose/.env`. `it`, `es` and `de` are accepted but have no clerk sentences of their own yet, so they fall back to English with a startup warning.
- An absent write half is a supported state: none of `CLERK_OWNER_PUBKEY`, `CLERK_GATEWAY_URL` and `CLERK_GATEWAY_SESSION_FILE` set is lot 1's clerk with one `warn` at startup naming the three, so a ✅ that decides nothing is announced rather than discovered; some but not all is a startup refusal naming the missing ones.
- **Two clerks on one key are unsupported.** Both may write the same suggestion or line in the window between one's query and its post; nothing corrupts and the sweep deletes both, but the owner sees two. One clerk per relay key.

## Configuration

Environment variables, like every other Twalk component. `CLERK_RELAY_URL`, `CLERK_NOSTR_KEY_FILE` and the three `CLERK_CHANNEL_*` are the ones with no default: empty on any of them and the clerk (in the reference deployment) starts, says so, and hosts nothing — `deploy/docker-compose/clerk-entrypoint.sh` is what makes that true of the compose service specifically; the bare binary refuses to start on a missing one.

| Variable | Required | Meaning |
| --- | --- | --- |
| `CLERK_RELAY_URL` | yes | The URL the owner's Buzz relay **announces** (its own `RELAY_URL`): `http://` or `https://`, a host and optionally a port, nothing after — no trailing slash, no path. |
| `CLERK_NOSTR_KEY_FILE` | yes | Path to the clerk's own signing key: one line, 64 hex characters or `nsec1…`, or an env-style `BUZZ_PRIVATE_KEY=<key>` line (what `provision-nostr-key.sh` writes). Refused if the file is readable by group or others — it signs everything the clerk posts. |
| `CLERK_CHANNEL_APPROVALS` | yes | The `approbations` channel's UUID, as `provision-buzz-channels.sh --bot <hex>` prints it. |
| `CLERK_CHANNEL_ACTIVITY` | yes | The `activite` channel's UUID. |
| `CLERK_CHANNEL_JOURNAL` | yes | The `journal` channel's UUID. |
| `CLERK_USER_LANGUAGE` | | The language the clerk writes its own sentences in — never a contact's, which it never quotes. One of `en`, `fr`, `it`, `es`, `de`. Unset runs as `en` and warns at startup (`CLERK_USER_LANGUAGE is not set; the clerk writes in English. Set it in deploy/docker-compose/.env`), because the clerk cannot read the language set in the Companion. Refused at startup otherwise, with the five named. |
| `CLERK_NATS_URL` | | Default `nats://localhost:4222`. |
| `CLERK_STREAM` | | The JetStream stream name. Default `twalk`. |
| `CLERK_SUBJECT_PREFIX` | | This deployment's bus namespace: `fr.linagora.twalk.X` becomes `<prefix>.X`. Default `twalk`. |
| `CLERK_LISTEN` | | Where `/health` and `/metrics` are served. Default `127.0.0.1:8084`. |
| `CLERK_SWEEP_SECONDS` | | How often the sweep looks for an expired suggestion's post to delete. Default 60; refused below 1. |
| `CLERK_LOG_LEVEL` | | Default `info`. |
| `CLERK_OWNER_PUBKEY` | write half | The owner's Nostr public key, 64 hexadecimal characters (uppercase is lowercased; `npub1…` is refused): the one key whose ✅ is an approval. From configuration, never read off the relay. |
| `CLERK_GATEWAY_URL` | write half | The Companion Gateway's origin — `http://` or `https://`, host and optionally a port, no path, no trailing slash — because the clerk builds every request path onto it. In the reference deployment, `http://127.0.0.1:<GATEWAY_HTTP_PORT>` unless set. |
| `CLERK_GATEWAY_SESSION_FILE` | write half | The file holding `TWALK_GATEWAY_REFRESH_TOKEN=<token>` — the refresh token of the owner's `Buzz` device, as `provision-clerk-device.sh` writes it. The clerk rewrites it on every refresh, atomically, so its **directory** must be writable by the clerk; refused if group or others can read it. In the reference deployment it is `/var/lib/clerk/session`, inside the directory `CLERK_GATEWAY_SESSION_DIR` mounts. |
| `CLERK_DECISION_SECONDS` | | How often the decisions loop reads the gestures on the clerk's own posts. Default 5; at least 1 — a zero is refused at startup rather than panicking the loop behind a green `/health`. |

The three "write half" variables go together: all three set is the write half on, none is off (with a startup warning), and any other combination refuses to start naming the missing ones.

An environment variable that is absent or empty is unset either way: an empty value in a compose `.env` file is how an operator leaves an option out.

### `/health` and `/metrics`

`/health` answers as soon as the origin is bound, before the bus is reached — a late bus does not make the process look down. `/metrics` renders, at zero when nothing has happened yet:

- `twalk_clerk_posts_total{channel}` — posts written to the relay, by channel (`approbations`, `activite`, `journal`).
- `twalk_clerk_deleted_total{why}` — posts the sweep deleted: `expired` (the reference line's `expires_at` had passed) or `undatable` (no expiry the sweep could read, and the relay's own `created_at` seven days old — ADR 0028's ceiling).
- `twalk_clerk_skipped_total{why}` — events read off the bus that did not become a post or a line (`expired`, `unreadable`, `duplicate` — the last on any of the three channels), and events read back off the relay that were dropped because their signature does not verify (`unverified`: a number here that is not zero is a relay to look at).
- `twalk_clerk_approvals_total{outcome}` — gestures on `approbations` posts carried to their outcome (#284): six fixed rows at zero from the start — `approved`, `already_approved`, `refused_locally` (a ❌), `not_the_owner`, `gateway_unreachable`, `unauthenticated` (the device revoked, or its refresh token dead) — and one row per Companion Gateway refusal code (`consent_revoked`, `suggestion_expired`, …) as it occurs, so the vocabulary is the Gateway's here too.
- `twalk_clerk_relay_failures_total` — failed writes to the relay (a post, a delete, a query).
- `twalk_clerk_sweeps_total` — completed sweep passes.
- `twalk_clerk_up`, `twalk_clerk_started_at_seconds`.

## Operator steps

Three, in this order, before anything above is set — `deploy/docker-compose/.env.example`'s Clerk section has the same list with the deployment's own paths:

1. `./provision-nostr-key.sh /etc/twalk/clerk.env` — generates the clerk's key, prints its public half, and names the relay-side step: `./run.sh add-member <hex>` in Buzz's own compose bundle, because a relay with restricted writes refuses a key it was not told to accept.
2. `./provision-buzz-channels.sh --bot <that hex pubkey>` — creates the owner's channels (as the owner, from a key the script never prints), adds the clerk as a `bot` member of each, and prints the three `CLERK_CHANNEL_*` lines ready to paste.
3. Paste what was printed into `deploy/docker-compose/.env`, then `docker compose up -d clerk`.

Two more for the write half (#284), in this order:

4. Set `CLERK_OWNER_PUBKEY` (the owner's own public key, as `provision-buzz-channels.sh` prints it) and `CLERK_GATEWAY_SESSION_DIR` (a host directory for the session) in `.env`.
5. `./provision-clerk-device.sh`, with the Gateway and Synapse up — the owner's Matrix password at the terminal (or `TWALK_OWNER_PASSWORD_FILE`), never an argument and never echoed; one Matrix OpenID token; one `POST /api/session` as the device `Buzz`; the refresh token written into that directory at mode 0600, beside it and renamed over. The Matrix login it made for the token is logged out at the end. Then `docker compose up -d clerk`. Run it again when the device is dead — revoked on the dashboard, or asleep for thirty days — and it restores the one `Buzz` without a second, then `docker compose restart clerk` (a running clerk would also find the new session by itself at its next hourly retry; `up -d` does not restart an unchanged container). It is safe to run beside a running clerk: on an alive session it refreshes in place, and if the two refresh at the same moment one of them gets a `401` on the token the other rotated away — the clerk recovers on its next retry because it re-reads the file, so that is a delay and not a loss.

The clerk runs in the **host's** network namespace (`network_mode: host`), because the relay is reached by the URL it announces, the same shape `hermes` is in for the same reason — and it is also why `http://127.0.0.1:<GATEWAY_HTTP_PORT>` is the right default for `CLERK_GATEWAY_URL` there. The compose service mounts the session **directory** read-write at `/var/lib/clerk` and its entrypoint (`deploy/docker-compose/clerk-entrypoint.sh`) hands it and the file to the unprivileged `clerk` account before dropping privileges; the host directory therefore belongs to that account after the first start — which is why it must be a directory of its own, holding nothing but the session: the entrypoint refuses to take over one that holds anything else — and an operator who is not root runs the script again with `sudo --preserve-env=TWALK_OWNER_PASSWORD_FILE` (a plain `sudo` drops that variable); the file the script writes as root keeps the container's account as its owner, so the running clerk goes on reading it. A directory set with no session in it, or an owner's key with no directory, is refused at start naming the script rather than left to a crash loop reading "No such file".

## What is deliberately not here

- **The delivery line.** An `approbations` post says, in so many words, that its delivery line is not yet known. That line is `GET /api/suggestions`'s `delivery` — `can_reach` or `cannot_reach`, the owner's own account's standing in the trigger's room, read by the Companion Gateway as the bridge's bot ([#216](https://github.com/linagora/twalk/issues/216)) — and the clerk does not read it, because the decisions loop makes one request per gesture and reading a listing on every post is a different budget and a different lot. (The `journal` line's `reach` is a different fact: the Sensor's own report, after the post, of whether the reply went to the contact or to nobody.)
- **Any decision of the clerk's own.** A ✅ becomes an approval because the owner made it and the Companion Gateway accepted it; the clerk refuses nothing on its own account, edits nothing, and carries no approval the Gateway did not record. A Gateway's refusal is relayed in the Gateway's words and left standing: the post stays, for the owner or the sweep.

## Tests

```bash
cd clerk
cargo test   # boots the shared test stack (Synapse, NATS) and a real Buzz relay of its own (Docker required)
```

Integration tests in `clerk/tests/` run the clerk binary at its process boundary (`ClerkProc`, modelled on the Hermes suite's `RuntimeRun`) against the shared harness's Synapse/NATS stack and a **real Buzz relay** the suite brings up itself, seeded by signed events the way an operator seeds the owner's own relay — `smoke.rs`, `approbations.rs` (one post per suggestion across a redelivery and a restart, and a trigger whose body, excerpt, display name and `network_identifier` are distinctive markers searched for in every event of every channel), `journal.rs` (both languages, and one line per report across a redelivery of a report dated past the relay's fifteen-minute window), `activite.rs` (one line per transition across a redelivery), `sweep.rs`, and `decisions.rs` (#284) — the write half against a **stub Companion Gateway** (`tests/harness/gateway.rs`, ports 17400–17499, the shape the Hermes suite's stub has), because the real one needs a Synapse owner and belongs to the deployment suite: a ✅ by the owner is one approval call and the post is gone, across a second tick and a restart; a reply approves with its text and a redelivery of it sends once; a stranger's ✅ makes no call and is answered once; every refusal code the Gateway documents is answered with the Companion's sentence, taken from `companion-gateway/openapi.yaml` by the same walk `refusals.rs`'s own test makes, so the table cannot drift; `already_approved` is success; a revoked device is named in the thread and the ✅ is carried after the script's file is restored; an unreachable Gateway is retried and then said; and nothing of the owner's reply reaches a log or `activite`. The unit test in `refusals.rs` is the ticket's two-way check: every code `approveSuggestion` documents has a sentence in both catalogues, and every sentence the clerk knows is a documented code — the Rust mirror of `companion/src/lib/approvals/refusal.test.ts`.

The ticket's container-environment criterion — the clerk's container holds a refresh token and nothing else of the Gateway's: not the service token, not a device token at rest — is asserted on a container Docker really started by the deployment suite. What guards it here is a unit test on the compose file itself (`config.rs`, `the_compose_service_holds_no_gateway_or_hermes_credential`): it reads the `clerk` service's `environment:` block out of `deploy/docker-compose/compose.yaml` and fails on any variable that is not `CLERK_*`, or whose value names `GATEWAY_SERVICE_TOKEN`, a `HERMES_*` variable other than the `HERMES_USER_LANGUAGE` fallback, `BUZZ_PRIVATE_KEY`, or anything ending in `_TOKEN` or `_SECRET`. `CLERK_GATEWAY_URL: ${CLERK_GATEWAY_URL:-…}` naming the Gateway passes, deliberately: the write half's credential is in a mounted file and never in that block.

The relay stack (`clerk/tests/compose.relay.yaml`: the relay, Postgres, Redis, nothing else) is its own compose project, under its own variables:

| Variable | Default | Meaning |
| --- | --- | --- |
| `TWALK_CLERK_TEST_STACK` | `twalk-clerk-test` | The compose project name. |
| `TWALK_CLERK_TEST_RELAY_PORT` | `17800` | The relay's published port on `127.0.0.1`; also part of the URL every signed request in the suite is bound to, since the relay is multi-tenant by host. |

Like the shared test stack, the relay stack **persists across runs** — every channel a test creates is a fresh UUID, every clerk key is fresh, and every run has a bus stream and subject prefix of its own, so nothing about a previous run's state has to be cleaned up for the next one to be isolated. It goes down with:

```bash
docker compose -p twalk-clerk-test -f clerk/tests/compose.relay.yaml down -v
```

(substituting `TWALK_CLERK_TEST_STACK`'s value for `twalk-clerk-test` if it was set to something else).
