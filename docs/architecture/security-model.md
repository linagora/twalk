# Security model — which component holds which secret, and what is not protected

Twalk's promise is that no message leaves the user's infrastructure without their consent. This document states what that promise rests on: which component holds which secret, what is encrypted and what is not, where the trust boundaries run, and what consent does and does not do. It is written for an operator deciding whether to run Twalk on their own hardware, so it states residual risk plainly rather than reassuring.

Vocabulary is [`CONTEXT.md`](../../CONTEXT.md)'s. Two markers run through the document, because much of the design is decided and not yet built:

- **Today** — true of the code in this repository: the Sensor (`sensor/`) and the reference deployment (`deploy/docker-compose/`).
- **Designed, not built** — settled by an ADR or a spec issue, with no code behind it. The Companion PWA is in this state: `companion/` holds a README. The Companion Gateway is now **partly built**: its origin ([#48](https://github.com/linagora/twalk/issues/48)), its authentication — Matrix OpenID sign-in, the owner check and per-device tokens ([#52](https://github.com/linagora/twalk/issues/52)) — its consent store, which records the owner's decisions and publishes them on the bus ([#49](https://github.com/linagora/twalk/issues/49)) — and its bootstrap — the registration relay for the first and only account, and the Sensor's invitation into the rooms the user chooses ([#53](https://github.com/linagora/twalk/issues/53)) — its bridge login facade — the Gateway drives each configured bridge's provisioning API with that bridge's secret, holds the blocking step of a QR login itself and exposes a pollable state ([#55](https://github.com/linagora/twalk/issues/55)) — and its consent snapshot, the whole current state with the bus sequence it reflects, read with a service token ([#50](https://github.com/linagora/twalk/issues/50)) — and its pending-contact projection, which makes the Gateway a *consumer* of the bus as well as its producer: a durable consumer on `inbound.message.received` that keeps a contact's Matrix ID, the network it wrote on and its first and last sighting, and nothing else ([#54](https://github.com/linagora/twalk/issues/54)) — all exist in `companion-gateway/`; and its bridge *status* half — the webhook each bridge pushes its connection state to, verified against that bridge's own `as_token`, reconciled at startup and published on the bus as `bridge.status.changed` ([#56](https://github.com/linagora/twalk/issues/56)). The Sensor reads that snapshot as of [#51](https://github.com/linagora/twalk/issues/51): it applies the whole state at startup and creates its `consent.state.changed` consumer at the sequence the snapshot names, so a restart no longer relabels a granted contact `pending` ([#16](https://github.com/linagora/twalk/issues/16)). The bridges have moved too: `mautrix-whatsapp` and `mautrix-signal` are part of the reference deployment as of [#73](https://github.com/linagora/twalk/issues/73), behind a compose profile, so the appservice credentials below are real files on a real volume — and as of #55 the provisioning secret among them is a credential the Gateway actually holds. Its use of the `as_token` is now built too, and narrow: verification of a status push, and nothing else. Hermes is built as of [#23](https://github.com/linagora/twalk/issues/23), on top of the persona SDK (`sdk/python/twalk_sdk`) and the reference persona `assistant` (`hermes/personas/assistant/`) from [#21](https://github.com/linagora/twalk/issues/21) — which means the consent gate below has code behind it on the consumer side, and a persona process holds the LLM credentials and sends message content to the endpoint the operator configured. Since [#158](https://github.com/linagora/twalk/issues/158) the runtime is a service of the reference deployment rather than something an operator starts by hand, which is what puts a Docker socket in the table below.

Last reviewed: 2026-09-18.

## Trust boundaries

Twelve boundaries matter. The important ones are not the network hops but the two places where encryption ends: inside a bridge, and inside the Sensor.

| Boundary | What crosses it | What protects it |
| --- | --- | --- |
| Network ↔ bridge | The user's traffic on WhatsApp, Signal, SMS, and the credentials that reach it | The network's own protocol. The bridge terminates it: this is where sovereignty starts, not where it holds |
| Bridge ↔ homeserver | Portal-room events, as an appservice | The bridge's `as_token` and the homeserver's `hs_token`, both in the appservice registration file |
| Homeserver ↔ Sensor | Megolm-encrypted portal-room events | End-to-end encryption. Synapse stores ciphertext it cannot read; it holds all the metadata |
| Sensor ↔ bus | Cleartext CloudEvents: bodies, attachment decryption keys, contacts | Nothing cryptographic. This is where end-to-end encryption ends, by design: normalisation needs plaintext |
| Bus ↔ consumers | Every event, replayable for **ninety days** and within two GiB, the oldest discarded first ([ADR 0037](adr/0037-the-bus-keeps-ninety-days-and-two-gigabytes-and-no-more.md)) | Network reachability only. In the reference stack the bus is bound to localhost and has no authentication |
| Browser ↔ Companion Gateway | The user's decisions, a Matrix OpenID token, network credentials in transit | TLS from the operator's reverse proxy, a per-device Gateway token, same origin ([ADR 0011](adr/0011-gateway-authenticates-with-matrix-openid.md)) |
| Companion Gateway ↔ homeserver and bridges | Account registration, bridge logins, status webhooks | Operator-supplied secrets in the Gateway's configuration — the powerful ones (see below). The status webhook is the one that comes *inward*, and it is authenticated by the calling bridge's own `as_token` rather than by its position on the network |
| Hermes runtime ↔ personas | Events, suggestions, replies | Nothing beyond the bus. Personas are separate processes with no privilege gap from third-party ones ([ADR 0008](adr/0008-hermes-rust-runtime-personas-as-processes.md)). A persona is handed a constructed environment and nothing else: no socket, no bind mount, and none of the runtime's own variables ([ADR 0015](adr/0015-no-default-llm-configured-through-the-companion.md)) |
| Hermes runtime ↔ the Docker daemon | "Start this image as this persona" | **Nothing.** Since [#158](https://github.com/linagora/twalk/issues/158) the reference deployment mounts the host's Docker socket into the `hermes` service, because a persona ships as an image and the runtime starts it ([ADR 0023](adr/0023-the-deployment-starts-personas-through-the-hosts-docker-socket.md)). The socket is an unauthenticated root-equivalent API: this boundary is a boundary in name only, and it is the widest grant in the deployment |
| Persona ↔ LLM | Whatever the persona sends to reason about an event | The operator's choice of model. A remote model is outside the user's infrastructure |
| Clerk ↔ Buzz relay | Suggestions' bodies, one post each and deleted when the suggestion expires or is decided; the clerk's own lines; the owner's gestures, read back | NIP-98 on every request, signed with the clerk's own key, which the relay was told to accept; the relay's membership. A ✅ counts only when the **owner's** key signed it, read from configuration and never from the relay ([ADR 0036](adr/0036-the-clerk-approves-as-a-device-of-the-owner.md)) |
| Clerk ↔ Companion Gateway | One approval per ✅, and the session that authorises it | A device token of the owner's — the clerk is a device named `Buzz`, signed in with a Matrix OpenID token an operator minted, revocable from the dashboard — never a service token. Loopback on the reference deployment |

Two consequences are worth stating before the detail:

- **The Sensor is the chokepoint of confidentiality, not of encryption.** Everything downstream of it — the bus, Hermes, personas, oversight interfaces — reads message bodies in cleartext. What limits them is the consent label and their willingness to honour it, not cryptography.
- **A bridge sees everything on its network.** WhatsApp and Google still see exactly what they saw before Twalk existed, and the bridge sees it too, in cleartext, with the credentials to act as the user. Self-hosting moves that exposure onto the user's own machine; it does not remove it.

What the Companion Gateway deliberately does **not** hold, per [ADR 0011](adr/0011-gateway-authenticates-with-matrix-openid.md) — and, for the authentication and bootstrap halves, now asserted rather than promised: `companion-gateway/tests/signin.rs` signs a device in against a real Synapse, and `companion-gateway/tests/bootstrap.rs` creates the owner's account and invites the Sensor into a room, and both then read the Gateway's store and its captured log output for every credential involved — the user's Matrix access token, the OpenID token, the password the user chose and the registration shared secret itself. No Matrix access token for the user, no network credentials — a bridge login's cookies or QR payload pass through and are forgotten, which `companion-gateway/tests/bridges.rs` now asserts by reading the Gateway's whole state directory and its captured logs for the credential it just relayed — no recovery key, and no message content — its pending-contact projection stores a contact's Matrix ID, its network and timestamps, never a body, never a display name and never the contract's `network_identifier`, which since [#54](https://github.com/linagora/twalk/issues/54) is asserted rather than promised: `companion-gateway/tests/pending.rs` publishes an inbound event carrying all three and then reads the bytes of the Gateway's whole state directory, and its captured logs, for each of them.

The asymmetry is deliberate and uncomfortable: the Gateway holds no user credential and no message, but it does hold the two credentials that are most powerful on the homeserver — a registration secret that creates accounts, and an `as_token` that impersonates an appservice. ADR 0011 accepted that cost explicitly, and answers it with two narrow mitigations: the Gateway refuses any account creation after the first, and it uses the `as_token` within a bounded reach — verifying a webhook's sender, and acting as that bridge's **own bot** on the portal rooms that bot is already in. The only account it ever acts as is the bot the operator configured (`GATEWAY_BRIDGE_<ID>_BOT_USER_ID`, which is what the `?user_id=` on each call names): never a ghost, never a value derived from a request, never one assembled from a bridge id. And it never touches a room it did not itself read as a portal of that bridge, so a room id in a request cannot widen where the credential acts.

> **Correction, [#171](https://github.com/linagora/twalk/issues/171).** The sentence above read *"It never masquerades as a ghost (no `?user_id=` is ever sent)"* until the reference deployment proved that pair of claims incompatible. Acting as the bridge's own bot is exactly what `?user_id=` is *for*: with no `?user_id=`, an appservice token acts as its registration's `sender_localpart`, and a generated registration's sender is a random localpart in no rooms. So the Gateway was not acting as the bot at all — it read 32 portal rooms as `@jaay9HZ…:twalk.localhost` and reported zero. The decision never changed; the description of the mechanism was wrong, and the narrowing it claimed was unenforceable because it was false. The narrowing above replaces it and is the stronger one: the masquerade can only ever name an account an operator wrote in configuration, which is a property the code enforces rather than a habit it keeps. Neither mitigation changes what the credential would grant an attacker who read it, and ADR 0024 records why acting with it at all was preferred to the alternative, which was for the Gateway to hold a long-lived Matrix access token of the user's.

The first of those two is now code rather than intention, and it is worth stating exactly what it does and does not close ([#53](https://github.com/linagora/twalk/issues/53)). `POST /api/bootstrap/account` creates an account only when the username is the localpart of `GATEWAY_OWNER`, and only when no such account exists; the refusal is enforced twice over, by a row in the Gateway's own store whose table admits exactly one (`CHECK (id = 1)`) and by the homeserver's `M_USER_IN_USE`, so wiping the Gateway's volume does not re-open the window. The relay is also off unless the operator sets `GATEWAY_REGISTRATION_SHARED_SECRET`: an operator who provisions the account with `provision.sh` never enables it at all.

What that leaves is a bootstrap window, and it is real. The endpoint cannot require authentication, because it runs before the account that would authenticate anyone exists. So between the moment the relay is enabled and the moment the owner finishes screen 2, whoever can reach the Companion's origin can claim the owner's account with a password of their choosing — and would then be the owner as far as every later check is concerned. The window closes for good on the first success, and `.env.example` says so where an operator will read it.

## What is encrypted at rest, and what is not

**Encrypted, because Matrix encrypted it before it was stored.** Portal-room traffic sits in Synapse's database as Megolm ciphertext, and attachments sit in the media store as AES-CTR ciphertext with per-file keys. Synapse holds no key for either. That is the only at-rest encryption in the stack, and it covers message payloads alone — not the room graph, not memberships, not timestamps, not who talked to whom.

**Not encrypted: the Sensor's stores.** The Sensor opens its sqlite state and crypto stores with no passphrase (`sqlite_store(state_dir, None)` in [`sensor/src/main.rs`](../../sensor/src/main.rs)). The crypto store holds the Megolm keys, the cross-signing private keys and the key-backup key; the state store holds the room list and the sync token; `session.json` beside them holds the access token, written atomically with mode 0600. Anyone who can read that volume can read every room the Sensor can read.

This was decided, not overlooked. Issue [#14](https://github.com/linagora/twalk/issues/14) weighed a passphrase mechanism (an environment variable or a key file) against accepting the exposure, and accepted it: the host volume is the operator's to protect, with filesystem permissions and disk encryption. The reasoning behind that choice is worth keeping visible, because it is a judgment about a threat model rather than a claim of safety. The Sensor must open its store unattended on every restart, so any passphrase it could use has to live on the same host as the store — in the environment or in a file next to it. That defends against a disk that leaves the host, which is what full-disk encryption already defends against, while adding a new way for a restart to fail. The decision records one condition for revisiting it: if a hosted offering ever appears, the operator and the user stop being the same person and the trade-off changes.

**Not encrypted: the Gateway's session store.** `sessions.db` in `GATEWAY_STATE_DIR` holds the device list — each device's name, the dates it was created, last seen and revoked on — and SHA-256 digests of the tokens issued to it. Read access to that volume yields a social-adjacent fact (when the owner used which device) and the ability to revoke devices; it yields no credential, because a digest cannot be presented as a token and the Gateway holds no signing key to steal. Write access is another matter: anyone who can write the file can insert a device of their own.

**Not encrypted: the Gateway's consent journal.** `consent.sqlite3`, beside the session store in `GATEWAY_STATE_DIR`, opened with no passphrase for the same reason the Sensor's stores are, with the file narrowed to its owner (mode 0600) and the directory to 0700. It holds no message content — a decision is a subject, a state, a perimeter, two timestamps, the owner and an optional reason — but it is a social graph with timestamps: who the owner decided about, on which network, when. Anyone who can *write* that file edits the audit trail of a confidentiality promise; inside the Gateway the journal is append-only (sqlite triggers refuse deletes and rewrites of a recorded field), which is a guarantee about the service, not about the file.

**Not encrypted: the Gateway's pending-contact store.** The same `consent.sqlite3` file, in a table of its own ([#54](https://github.com/linagora/twalk/issues/54)): one row per (contact, network) with the Matrix ID of whoever wrote, and the first and last instants they did. Four columns, and the restraint is the whole of the protection — there is no message body, no display name and no `network_identifier`, because the projection parses three attributes of an inbound event and never its `data`. Unlike the journal beside it, this table is not append-only and holds no decision: it is a work queue, and the user emptying it is the point.

What it is, said plainly: **a list of who writes to the user, with timestamps** — the second half of the social graph the journal already holds, and the half the owner never chose. Note too what "only the Matrix ID" does not hide. A bridged ghost user's ID conventionally embeds the network identifier (`@whatsapp_33612345678:example.com`), so this table keeps phone numbers although it has no column for one; it stores the ID because a consent decision has to name its subject and that ID *is* the subject. See residual risk 5.

**Not encrypted: the Gateway's settings store, which holds an outbound secret.** `settings.sqlite3`, beside the other two in `GATEWAY_STATE_DIR` and narrowed to its owner (mode 0600), holds the model configuration and the user's native language ([#98](https://github.com/linagora/twalk/issues/98)) — and, when the owner set one from the Companion rather than supplying a file, **the LLM endpoint's credential in cleartext**. That makes it different in kind from the two stores above: they hold metadata about the user, and this one holds a key that bills money to somebody's account and can be used, from anywhere, to send whatever the holder likes to a model. An operator who does not accept that writes the credential into a file instead and points `GATEWAY_LLM_API_KEY_FILE` at it: the file then wins over anything set from the browser (ADR 0015), the browser's value is never used, and the secret's exposure becomes the file's permissions rather than this database's. That is the reference deployment's own shape. What stays true either way is that the Gateway must be able to hand the credential to the runtime unattended on every restart, so the reasoning of [#14](https://github.com/linagora/twalk/issues/14) applies unchanged: any passphrase it could use would live on the same host as the store. See residual risk 15.

**Not encrypted: everything else on disk.** Synapse's sqlite database, its signing key and its media store; the bus's JetStream file store; and `.env`, which holds every secret above in cleartext and is readable by anyone who can read the file or inspect the containers. No volume in the reference deployment is encrypted by the stack itself. Disk encryption, volume permissions and host hardening are the operator's, and the documentation says so rather than implying the containers handle it.

**The bus is the widest exposure, and it is not at rest only.** Events carry message bodies, contact identities and — since the contract gained encryption material on attachments ([#17](https://github.com/linagora/twalk/issues/17), closing the gap found in [#15](https://github.com/linagora/twalk/issues/15)) — the AES key of every encrypted attachment, in cleartext, for as long as the stream's retention keeps them — ninety days since [#174](https://github.com/linagora/twalk/issues/174) ([ADR 0037](adr/0037-the-bus-keeps-ninety-days-and-two-gigabytes-and-no-more.md)), where before that nobody had decided and it was for ever. The schema itself says the key must stay inside the user's infrastructure and must never be logged ([`inbound.message.received.schema.json`](../../contracts/cloudevents/v1/inbound.message.received.schema.json)). In the reference stack the bus has no authentication at all and is bound to localhost for that reason ([`compose.yaml`](../../deploy/docker-compose/compose.yaml)). A key alone does not fetch the file — Synapse's media API still wants an account — but a key plus any account on the homeserver does.

## The recovery-key boundary

Two different recovery keys exist in Twalk, and conflating them is the mistake this section is here to prevent.

**The user's recovery key belongs to the browser.** During account creation (screen 2 of [`docs/wireframes/companion-v0.1.md`](../wireframes/companion-v0.1.md)) the Companion generates the key client-side, shows it once, and offers a copy button and a PDF. [ADR 0011](adr/0011-gateway-authenticates-with-matrix-openid.md) makes this binding: the key is generated in the browser and never reaches the Gateway. The Companion is a static export with no secret of its own, and the Gateway relays registration without ever seeing the key that protects the account's secret storage.

Screen 2's copy — "Twalk never sees it" — is therefore a statement about where the code runs, and it holds on one condition, which is now a requirement on the PWA and not a matter of taste: the key must be generated by the browser, used in the browser to encrypt the cross-signing secrets, and only the ciphertext and the key's own description may be uploaded to the homeserver. Matrix's secret storage is built for exactly this, so meeting the condition costs nothing — but an implementation that posted the key to the Gateway "to make recovery easier" would break a promise the user was shown in plain language.

The Gateway's side of that condition is enforced rather than trusted ([#53](https://github.com/linagora/twalk/issues/53)): its registration relay takes a username and a password and refuses a body with any other field, so there is no field a key could arrive in, and a request carrying anything recovery-key-shaped is answered `400 recovery_key_refused` instead of being quietly ignored — a client with that bug finds out at once. The relay's answer is the Matrix session and nothing more (`user_id`, `device_id`, `access_token`, `home_server`), which `companion-gateway/tests/bootstrap.rs` asserts on the response's field list. That makes an implementation which posted the key a build failure on the PWA side rather than a silent breach of the promise.

**The Sensor has its own key, because it is a different account.** The Sensor logs in as `@sensor:<domain>`, a Matrix account of its own with its own device, its own cross-signing identity and its own server-side key backup, created automatically when none exists. `SENSOR_RECOVERY_KEY` is that account's recovery key, saved by the operator during onboarding and read from `.env`. It is not the human's, and it could not be: the human's key opens the human's secret storage, which has nothing the Sensor needs, and putting the human's key in a server-side environment variable is precisely what ADR 0011 and screen 2 rule out.

The trade-off is symmetric and small in both directions. Set, `SENSOR_RECOVERY_KEY` lives in `.env` and in the container's environment, and its blast radius is the Sensor account's backed-up room keys — the traffic of the rooms the Sensor was invited to, nothing on the user's own devices. Unset, the Sensor decrypts live traffic anyway, because senders share Megolm keys with its device directly, but a replacement device loses everything from before it existed. The Sensor says so loudly in the log when it has to start on a clean crypto store.

## Consent as a confidentiality guarantee

Consent is not a preference the interfaces render. It decides what leaves the homeserver onto the bus, and what a persona may read once it is there. The Companion Gateway is its single writer ([ADR 0006](adr/0006-consent-state-owned-by-companion-gateway.md)); consumers read a snapshot naming the stream position it reflects and follow the stream from there ([ADR 0010](adr/0010-consent-snapshot-then-deltas.md)); activating or pausing a persona is itself a consent decision, scoped to the networks that persona may read ([ADR 0013](adr/0013-persona-activation-is-a-consent-decision.md)).

The three states protect different things, and only one of them is enforced by the producer:

- **`granted`.** The full event is published. Everything downstream may read it.
- **`pending`.** The Sensor labels, consumers refuse ([ADR 0012](adr/0012-revoked-consent-reduces-publication.md)). The body **is** on the bus. For a pending contact the guarantee is a convention honoured by consumers, not a property of the event — worth knowing before trusting a third-party persona. For a persona written against the SDK, honouring it is not left to the author: the gate lives in `sdk/python/twalk_sdk/consent.py` and drops every event whose consent extension is not exactly `granted` before persona code runs and before the LLM client is touched, which `hermes/tests/assistant.rs` asserts by absence — no event, and no completion request ([#21](https://github.com/linagora/twalk/issues/21)).
- **`revoked`.** The Sensor still publishes an inbound event, but carrying no content ([ADR 0012](adr/0012-revoked-consent-reduces-publication.md)). The event keeps its deterministic id, network, consent label, both timestamps, room and sender references, reply and thread relations, the contact's display name, and each attachment's shape — kind, media type, size, dimensions, duration. It drops everything that is the message: the body (which, for a media message, is also where a filename would travel), the reply excerpt and the reaction target's excerpt, and inside each attachment the `mxc://` reference, its decryption material and its caption. A reference plus the key that opens it is the content, so the two go together. Publishing nothing at all was rejected: the user would lose the evidence that a message arrived, and a broken bridge would become indistinguishable from a silent contact. Unlike `pending`, this state is enforced by the contract, not only honoured by the producer: `inbound.message.received.v1` makes such an event *invalid* if it carries a body, an excerpt or a media reference under a `revoked` label ([#58](https://github.com/linagora/twalk/issues/58)).

**One label, two people — the excerpts.** The three states above label one person: the sender of the event, named in its `subject`. Almost every field in an inbound event is that sender's own, and reduction on their label alone is therefore complete — for all but two fields. A reply's `reply_to.excerpt` and a reaction's `target.excerpt` quote a message **somebody else** wrote, which in a group is routinely a different contact, and the envelope carries a single `consent` extension that every consumer gates on. An excerpt published on the sender's label alone thus travels under a label that is not its author's: a granted contact reacting to a revoked contact's message put the revoked one's words on the bus in cleartext, inside an event marked `granted`, past the SDK gate that would have refused that same person's own event ([#110](https://github.com/linagora/twalk/issues/110) — observed live on a real WhatsApp group through the reference deployment; in a one-to-one conversation the quoted author is the user or the sender themselves, which is why it stayed invisible).

So both decisions have to be in the right state. The Sensor publishes an excerpt only when the sender's own consent does not reduce publication **and** the author of the quoted message is `granted`. Anything short of a grant withholds it, deliberately: an author the Sensor cannot resolve to a contact, and a message it cannot fetch or decrypt — unknown is not consent — and also `pending`, which in the Sensor's consent cache *is* the absence of a decision ([`CONTEXT.md`](../../CONTEXT.md): an absent subject means "never decided") rather than a weaker yes. The one person exempt is the owner: the user's own messages, and the replies the Sensor sends on their behalf, are not a third party's content, and there is no decision about the user to consult — so they are quoted exactly as before, whoever is quoting them and whatever the user decided about *them*. Since [#109](https://github.com/linagora/twalk/issues/109) that exemption is the Sensor's own Matrix ID **and** every identity the deployment has confirmed as the owner's, so a message the user sent from their own phone is quoted as their own words rather than withheld like a contact's ([ADR 0018](adr/0018-the-users-own-messages-are-their-own-event-type.md)). It is confirmed and never guessed: the owner's ghosts are handed to the Sensor as a set (`SENSOR_OWNER_IDENTITIES`), matched whole, and never recognised by display name — a contact chooses their own, so matching by name would hand them the exemption for the price of a rename. An identity the deployment did not confirm stays a contact, which is the safe direction of the remaining gap: an owner ghost nobody listed is treated as a stranger, never the reverse. [#147](https://github.com/linagora/twalk/issues/147) extended the same exemption, and the same confirmation rule, to the owner's own reactions ([ADR 0021](adr/0021-the-owner-is-never-a-contact-on-any-event.md)): reacting to a contact is not a way around the user's decision about that contact, so the excerpt a reaction carries is governed by the *target author's* state exactly as a reply's is.

What is withheld is the quotation, never the event. The reaction still publishes with its emoji, the reply still publishes with the sender's own body, and both keep the reference to the message they point at — the user keeps the evidence that the exchange happened. Where the contract allows it the field simply goes: `inbound.reaction.added.v1` leaves `target.excerpt` optional unconditionally. On a reply it is present and empty instead, because `inbound.message.received.v1` requires `reply_to.excerpt` from any sender not `revoked` — which is the same empty excerpt the Sensor has always published for a parent it could not read, so a consumer needs no new case, and cannot tell a withheld quotation from an unreadable one.

**What `revoked` stops:** future publication of that contact's message content — bodies, excerpts and media references alike — from the moment the Gateway records the decision and the Sensor applies it; and, since [#110](https://github.com/linagora/twalk/issues/110), their words quoted inside another contact's event as well.

**What `revoked` does not erase,** stated as a list because every item has surprised someone:

- events already on the bus, which stay until retention expires — ninety days ([ADR 0037](adr/0037-the-bus-keeps-ninety-days-and-two-gigabytes-and-no-more.md)) — and remain replayable in full;
- the portal rooms and the media store on the homeserver, which are untouched;
- the bridge's own store, and the external network's servers, which never heard about the decision;
- the Gateway's pending-contact projection, which keeps the contact's identity and timestamps;
- anything a persona already read, cached, or sent to an LLM.

Revocation applies to the future only. Erasing a contact's history is a separate, explicit action, scheduled for v1.0 alongside audit export and import ([`roadmap.md`](roadmap.md)). ADR 0012 rejected conflating the two in both directions: it surprises the user who only wanted to stop, and deceives the one who believed they had erased.

Two more properties follow from the design. A paused persona is not de-provisioned: it keeps running and receives nothing, and it keeps whatever it already had. And activation never spreads — connecting a new network leaves every persona inactive on it until the user says otherwise, which is the one behaviour the project exists to prevent.

Today the owner can take a decision: the Gateway records it in its journal and publishes it on the bus ([#49](https://github.com/linagora/twalk/issues/49)), and a Sensor running alongside applies it from then on. The restart used to be the failure mode, and it failed closed: the Sensor's consent cache is in memory, so a restarted Sensor resumed at its durable consumer's ack floor and labelled every sender it had not since heard a decision about `pending` ([#16](https://github.com/linagora/twalk/issues/16)). Both halves of the cure now exist: the Gateway serves the whole state with the stream sequence it reflects ([#50](https://github.com/linagora/twalk/issues/50)), and the Sensor applies that state at startup and creates its consumer at the sequence after it ([#51](https://github.com/linagora/twalk/issues/51)). What remains is a Gateway the Sensor cannot reach, and it still fails in the safe direction: the Sensor starts anyway — a Sensor that waited for its Gateway would lose inbound events — labels `pending`, says so in its log and counts it in `twalk_sensor_consent_snapshot_failures_total`, and retries until the snapshot answers. Over-labelling as `pending` is the safe direction.

## Residual risks

Plainly, with no mitigation implied where none exists.

1. **No volume in the reference deployment is encrypted** (today). Read access to the Sensor's volume yields the Megolm keys and the session token; read access to the bus's volume yields the retained events, bodies and attachment keys included. This is the accepted consequence of [#14](https://github.com/linagora/twalk/issues/14).
2. **The Companion Gateway concentrates the homeserver's most powerful credentials** (today, when the relay is enabled and bridges report their status: the registration secret, and one `as_token` per bridge). It can create an account and it holds credentials that impersonate appservices. Compromising it reaches further than compromising the Companion, the bus, or any single bridge. Its own mitigations — refusing accounts after the first, comparing a pushed token as a digest rather than byte by byte, and acting with an `as_token` only as the bridge bot the operator configured, only in rooms it has read as that bridge's portals, and never as a ghost (ADR 0024, corrected by [#171](https://github.com/linagora/twalk/issues/171)) — constrain what the Gateway does, not what its secrets would allow. Holding the token at all is the price of not trusting the compose network, which was the alternative: every container on that network can reach the Gateway's webhook port, so an unauthenticated webhook would let any of them tell the user a dead session was healthy.
3. **The registration relay's bootstrap window is unauthenticated by construction** (today, when `GATEWAY_REGISTRATION_SHARED_SECRET` is set). Until the owner's account exists, whoever reaches the Companion's origin can create it with their own password and become the owner. It closes on the first registration and never re-opens, and it never opens at all for an operator who provisions the account by hand — but while it is open, the origin's reachability is the only thing limiting who walks through it.
4. **Network credentials live inside the bridges** (today, for a bridge a human has logged in). The Gateway relays them and forgets them, so the Gateway is not where they are stolen: each bridge is, and each is a full account takeover surface for one network. Bridges are upstream software Twalk does not fork, so their storage and their exposure are theirs — which is also why their image versions are pinned rather than tracking `:latest` ([`bridges/README.md`](../../bridges/README.md)).
5. **Message metadata accumulates in the Gateway's stores** (today, both of them: the consent journal and, since [#54](https://github.com/linagora/twalk/issues/54), the pending-contact projection). No bodies, no display names and no `network_identifier`, but who the owner decided about *and* who contacted them, on which network and when: a social graph with timestamps, in a service reachable from the browser. The owner chose the first half; the second accumulates on its own, from whoever writes to them. Note also that a bridged Matrix ID conventionally embeds the network identifier (`@whatsapp_33612345678:example.com`), so storing the Matrix ID keeps the phone number even though neither store has an identifier field of its own — "only the Matrix ID" is not as neutral as it sounds, and it is stored because a decision has to name its subject. What constrains the projection is that it holds four columns and no more, which is enforced by the schema and asserted by a test that reads the store's bytes, not by care. The consent journal is append-only by design and therefore never pruned: a decision the owner later reversed is still in it, which is exactly what makes it an audit trail. The projection is not append-only, and a contact the owner decides about stays in the seen-contacts table even after it leaves the pending list — erasing a contact's history is a separate, explicit action and out of v0.1 ([ADR 0012](adr/0012-revoked-consent-reduces-publication.md)).
6. **The bus has no authentication** (today). Subject filtering is not a permission. Anything that can reach the bus port reads every event and can replay the stream.
7. **`pending` is enforced by consumers, not by the Sensor** (today). A persona that ignores the label reads bodies it was never granted. What [#21](https://github.com/linagora/twalk/issues/21) changes is where honouring it lives for a persona built on the SDK — in the SDK, before the author's code, so that forgetting is not possible — and what it does not change is who the guarantee rests on: anything that reaches the bus and does not use the SDK is bound by convention alone.
8. **Every secret sits in cleartext in `.env` and in container environments** (today), including the Sensor's account password and, when set, its recovery key.
9. **One owner, no isolation between humans** (today, for authentication). A deployment serves one person on any number of devices: the Gateway accepts exactly the Matrix ID in `GATEWAY_OWNER` and refuses every other identity the homeserver would vouch for. There is no multi-user separation to lean on — every device of the owner has the same, total access to the Gateway's API, consent included — and the refusal to create a second account ([#53](https://github.com/linagora/twalk/issues/53)) is also the weak point in any recovery story that loses the owner's identity. Note too what the owner check rests on: whoever controls the homeserver controls who the Gateway believes, because the homeserver is what answers the userinfo call.
10. **A remote LLM moves message content outside the infrastructure** (today, as of [#21](https://github.com/linagora/twalk/issues/21)). Consent gates whether a persona reads an event; it does not gate where that persona reasons. The `assistant` persona sends the message body, with a system prompt and nothing else, to whatever `TWALK_LLM_BASE_URL` names — a model on the same machine, or a hosted one. There is no default endpoint and no default model, and a persona refuses to start without both ([ADR 0015](adr/0015-no-default-llm-configured-through-the-companion.md)), so this is always a choice someone made; an operator who configured a hosted model has consented to it, and should know they did. When agent tracing lands ([ADR 0017](adr/0017-agent-observability-is-otlp-and-opt-in.md), [#99](https://github.com/linagora/twalk/issues/99)) the content switch will add a second copy of that content, in the tracing backend, under that backend's retention rather than the bus's — designed, not built, and named here because the switch will look technical and be a privacy decision.
11. **The Sensor's invitation allow-list is the only control on which rooms it joins** (today). `SENSOR_ALLOWED_INVITERS` names the accounts whose invitations are honoured, and a bridge's provisioning user is on that list — so a compromised bridge can put the Sensor into a room of its choosing.
12. **The owner is recognised from a list the deployment maintains by hand** ([#109](https://github.com/linagora/twalk/issues/109), [ADR 0018](adr/0018-the-users-own-messages-are-their-own-event-type.md)). The user's own messages no longer go out through the inbound door: they are `outbound.message.sent`, with the owner's Matrix ID as the subject and no consent extension at all, and the SDK refuses to wake a persona on that type beside the consent gate. Since [#147](https://github.com/linagora/twalk/issues/147) their own reactions are `outbound.reaction.added` on the same terms and their own presence is not published at all ([ADR 0021](adr/0021-the-owner-is-never-a-contact-on-any-event.md)) — which closed a real leak, not a modelling debt: the Sensor's consent cache falls back to a network's default before `pending`, so on a deployment where the user had granted a whole network their own reaction came out labelled `granted`, and a `granted` label is what attaches `network_identifier` — the phone number their own ghost localpart is minted from, published as a contact's attribute under a label asserting a third party had agreed to it. What remains is the identity. A bridge relays the owner under *network ghosts* of their own account — several per network, `@whatsapp_<phone>` and `@whatsapp_lid-<lid>` for one WhatsApp login — and nothing resolves that set today: a bridge's provisioning `whoami` reports a login id and no ghost Matrix ID at all, and deriving one by string concatenation finds the phone ghost and misses the LID ghost the messages actually arrive under. So the set is configuration (`SENSOR_OWNER_IDENTITIES`), and a ghost that starts being used and is not added is published as a contact's message again — labelled `pending`, gated like a stranger's. The failure is in the safe direction, and it is silent, which is why it is named here. One half of the invariant is not the Sensor's to close: it can refuse to *use* a consent row about the owner, from the snapshot or the stream alike, but it cannot remove one from the Companion Gateway's store, and a deployment upgraded across [#109](https://github.com/linagora/twalk/issues/109) can still hold a row about an owner ghost that the user's own messages put in the pending-contact projection before it. That half is [#149](https://github.com/linagora/twalk/issues/149): until it lands, "the owner never appears in the consent snapshot" is true of what the Sensor uses and not of what the Gateway stores.

13. **The reference deployment gives one of its services root on the host** (today, as of [#158](https://github.com/linagora/twalk/issues/158), for a deployment that hosts any persona). The `hermes` service holds the Docker socket, because a persona ships as a container image and the runtime starts that image ([ADR 0023](adr/0023-the-deployment-starts-personas-through-the-hosts-docker-socket.md)). Anything that compromises the runtime — a bug in it, a malicious argv in `HERMES_PERSONAS`, an operator tricked into adding a persona — reaches the whole host, not just Twalk: this is now the most powerful thing in the deployment, ahead of the Gateway's homeserver credentials in risk 2. Three things narrow it and none of them closes it: a persona container is handed no socket, no bind mount and none of the runtime's own variables, so the third-party persona ADR 0008 is about does not inherit the grant; `HERMES_DOCKER_SOCKET` can point at a rootless daemon, which makes the grant the operator's own account rather than root; and an operator who sets no persona holds no socket in practice, because the service then hosts nothing. The same service also runs in the **host's network namespace**, so it and its personas can reach every service bound to the host's loopback — Synapse and the Companion Gateway included — which the compose network would otherwise have separated. That arrangement is what lets a persona reach an LLM proxy on `127.0.0.1`, which is the reference deployment's own shape, and it is a second concession rather than a consequence of the first. Until a persona supervisor with a narrow grant exists, an operator who cannot accept this runs the Twalk stack without personas and loses the loop.
14. **A contact is never told their conversation is processed, and never asked** (open, [#122](https://github.com/linagora/twalk/issues/122)). Twalk decrypts a contact's messages, publishes them on a bus and submits them to a language model. Every disclosure the product makes is addressed to the user — the WhatsApp ban risk, the Google Messages cookie — and none to the person on the other side. The word "consent" in this project names *the user's* decision about a contact, not the contact's agreement; the glossary said otherwise for months, which is how this went unnoticed. What a contact should be told, by whom, and what their refusal would mean in a model whose three states are all the user's to set, is genuinely undecided and is being instructed rather than guessed. A persona's reply disclosing itself ([ADR 0019](adr/0019-a-persona-discloses-itself-to-the-contact.md)) is a different mechanism and does not close this.
15. **The LLM endpoint credential sits in cleartext in the Gateway's store, and it is a spending key** (today, when the owner sets one from the Companion — [#98](https://github.com/linagora/twalk/issues/98)). Every other secret the Gateway holds is either a digest it cannot present (device tokens, OpenID tokens) or a credential for a service inside this deployment (a bridge's `as_token`, the registration secret). This one is outbound and third-party: whoever reads `settings.sqlite3` can bill the operator's model account from anywhere, and — because the endpoint sees whatever a persona sends it — can point the deployment at an endpoint of their own by changing `base_url` in the same file. Three things constrain it and none of them encrypts it. It is write-only over the API, so no browser read and no log line carries it, which is asserted by searching every answer and every captured log line for it rather than left to care. It is only in the store at all when the owner typed it into a browser: an operator who supplies `GATEWAY_LLM_API_KEY_FILE` puts it in a file that **wins**, which is what the reference deployment does, and the browser's value is then never used. And the database is 0600 in a 0700 directory. The residual is the one [#14](https://github.com/linagora/twalk/issues/14) accepted for the stores beside it, with higher stakes, and an unencrypted volume is the operator's to protect.
16. **A leaked clerk key lets a stranger write onto the owner's Buzz channels** (today, [#265](https://github.com/linagora/twalk/issues/265)). The clerk signs with a Nostr key of its own, held as a host file (`CLERK_NOSTR_KEY_FILE`, mode 0600) and copied into a tmpfs for the unprivileged `clerk` account to read — never the container's writable layer, so a compromise of the running container does not put the key on disk anywhere new, but the host file itself is a plain, unencrypted secret like every other one in this table. Anyone who can read it can post as the clerk — one forum post per suggestion, one line per posted reply, an answer in a thread — on the channels `provision-buzz-channels.sh --bot` added it to, and only there: the key opens nothing on the Gateway, the bus or the homeserver. Since [#284](https://github.com/linagora/twalk/issues/284) the clerk does hold a Gateway credential (risk 17), but it is a different file, and the two do not compose into an approval: a ✅ is carried only when the **owner's** key signed it — `CLERK_OWNER_PUBKEY` is configuration and never read off the relay, and the clerk **verifies the Schnorr signature of every event the relay serves** (`relay::verified`) before it can be a gesture, dropping and counting the ones that do not verify (`twalk_clerk_skipped_total{why="unverified"}`) — which the clerk's key cannot do, and which a relay that forges a `pubkey` field cannot do either; a gesture by any other key — a relay `admin` included — makes no Gateway call. The exposure ends when the owner removes the clerk from the relay and its three channels, and rotation is `provision-nostr-key.sh` followed by `provision-buzz-channels.sh --bot` again — the same two scripts that provisioned it the first time, run again.
17. **A leaked clerk session approves as the owner for up to thirty days** (today, [#284](https://github.com/linagora/twalk/issues/284), for a deployment whose write half is configured). The clerk is a device of the owner on the Companion Gateway ([ADR 0036](adr/0036-the-clerk-approves-as-a-device-of-the-owner.md)), and its refresh token is a plain file on the host (`CLERK_GATEWAY_SESSION_DIR/session`, mode 0600, owned by the container's unprivileged account after the first start) — the first credential in this deployment that is at once a human's right and a machine's possession. Whoever reads it holds a device of the owner until it is revoked or thirty days pass unused, and a device token opens the whole Gateway API, consent included, not only the one write the clerk makes with it: the Gateway does not narrow a device by what it is, and this document does not pretend otherwise. Three things constrain it and none of them encrypts it. It is **revocable like a phone**, from the dashboard, with no shell and no Twalk involvement, and the clerk says in the thread when that has happened rather than failing silently. Rotation is built in: every refresh rotates both tokens and the old refresh token dies at that moment, so a copy taken today is dead at the clerk's next refresh unless the thief refreshes first — in which case the *clerk's* next refresh is refused, which is the symptom to look for. And the stolen right is bounded by what the bus holds: an approval needs a suggestion that is live, consented and within the Gateway's bounded lookup, so the token cannot reach an arbitrary contact — only one a persona had a live suggestion for, with the persona's text or, since `final.body` is the thief's to write, any text at all, for the hour a suggestion lives. What it does not close is the residual [#14](https://github.com/linagora/twalk/issues/14) accepted for every store beside it: the file is cleartext on an unencrypted volume, and that volume is the operator's to protect.
18. **A leaked collector grant reads the owner's mailbox and calendars until the owner revokes it** (today, [#274](https://github.com/linagora/twalk/issues/274), for a deployment that runs the collector). The refresh token in `oidc/grant.json` is, with the client secret beside it, a standing right to the owner's own accounts at their organisation — larger than any other credential in this table, since every one of them opens something inside this deployment or one network, and this one opens the mailbox. Three things constrain it and none of them encrypts it. It is **revocable at the SSO**, by the owner, with no Twalk involvement, and the collector says on the bus when that has happened (`reconnect_required`, with the operator's next step in the hint) rather than failing silently. Rotation is the SSO's: every renewal rotates the refresh token and the old one dies at that moment, so a copy taken today is dead at the collector's next renewal unless the thief renews first — in which case the *collector's* next renewal is refused, which is the symptom to look for and the reason one process holds one grant. And the two halves are two files in two places: the secret on the host as the operator's own, the grant in a volume the container's unprivileged account owns, so a read of one is not yet a token request. What it does not close is the residual [#14](https://github.com/linagora/twalk/issues/14) accepted for every store beside it: cleartext on an unencrypted volume, the operator's to protect — and the SSO's, whose revocation is the only way to end a grant already copied.

## What would change this model

- A hosted offering: the operator and the user stop being the same person, and [#14](https://github.com/linagora/twalk/issues/14)'s decision has to be reopened along with everything else in this document that says "the operator's to protect".
- Erasure (v1.0): the first operation that reaches backwards through the bus, the homeserver and the projections at once.
- Authentication on the bus, and per-consumer authorisation: the change that would turn the `pending` convention into an enforced boundary.
- A second login per bridge instance, or a second human: both need a dimension the contract does not have yet.

Vulnerabilities are reported privately, following the process the [README](../../README.md#security) points at.
