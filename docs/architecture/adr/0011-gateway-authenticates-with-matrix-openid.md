# The Companion Gateway authenticates through Matrix OpenID, and holds no Matrix access token

The Companion obtains an OpenID token from the user's homeserver; the Gateway verifies it there, checks the identity against the single owner declared in its configuration, and issues its own per-device token. A deployment serves one human on any number of devices: each device signs in for itself, and the Gateway keeps a device list it can revoke. The Gateway never stores a Matrix access token, never stores network credentials (a bridge login's cookies or QR payload pass through and are forgotten), and holds only operator-supplied secrets from its configuration: each bridge's provisioning secret, each bridge's `as_token` for verifying its status webhook, Synapse's registration secret, and the Sensor's service token. The user's recovery key is generated in the browser and never reaches the Gateway.

Rationale: the Companion is a static export with no secret of its own, and the user already has a Matrix identity — one identity source for the whole system. Forwarding the user's access token instead would hand the Gateway full power over the account for no gain, and a separate pairing-code system would be a second identity source and a second attack path to test. The cost is accepted honestly: the Gateway does hold credentials powerful on the homeserver (an `as_token` impersonates an appservice, the registration secret creates accounts), which is why it refuses any account creation after the first, and why `docs/architecture/security-model.md` must say which component holds which secret.
