# The owner is never a contact on any event, and their presence is not published at all

A reaction the user adds from their own phone is published as `outbound.reaction.added`, a type of its own, with the operator's Matrix ID as the subject and **no `consent` extension at all** — the schema declares none and closes itself to extras, so a third-party producer cannot set one either. It carries no `contact` object. The user's own **presence is not published at all**: no type of its own, no event, on any subject. A contact's presence is published exactly as before. Which identities are the operator's is ADR 0018's set, unchanged and used unchanged: an exact match against what the deployment confirmed, and an identity that was not confirmed stays a contact, so failing safe here means publishing. The Sensor's consent cache also refuses entry to any decision about one of those identities, whether it arrives in the Companion Gateway's snapshot or on the `consent.state.changed` stream, and says so at `warn`: the owner has no consent state, so a row about them is a row that should not exist. `outbound.*` is now a family rather than a single type, and the Python SDK's trigger-type gate needed no edit to exclude its second member, because it is an allowlist.

Rationale: ADR 0018 settled messages and left the rest, and the rest was worse than a modelling debt. `ConsentCache::state` falls back to the **network's default** before `pending`, and granting a whole network is how a user with hundreds of contacts actually decides — so on an ordinary deployment the user's own reaction came out labelled `granted`, not `pending`, and `normalize::contact_entry` attaches `network_identifier` when the label is `granted`. On a phone-based network that identifier is minted from the ghost localpart. The deployment was publishing **the operator's own phone number as a contact's attribute, under a label asserting that a third party had agreed to it**. That is not a glossary disagreement; it is the system asserting a consent that was never given, about the one person who cannot give it.

The two halves get different answers, and the criterion is not symmetry — it is whether the event tells anybody anything. A reaction the user made is information: a persona, or the "unanswered conversations" view the roadmap wants, can use "this message has been acknowledged" exactly as ADR 0018's argument used "this conversation has been answered", which is why that ADR rejected simply dropping the user's messages and why this one rejects dropping their reactions. The ninth type's argument carries to the tenth unchanged: an envelope must not lie, a `consent` extension on an event with no contact in it is a lie, and a consumer that never subscribes to a type cannot be surprised by it — the property neither "a flag on the inbound type" nor "make the extension conditional" can offer, since both leave a consumer that forgets the check being triggered by the user's own traffic with nothing to say so. Ten types before the v1.0 freeze is the price, and it was paid deliberately rather than discovered.

The owner's own presence tells nobody anything they do not already know: the user knows whether they are online. It is also, on the reference deployment, the overwhelming majority of the stream — Synapse broadcasts a real user's presence transitions to everyone sharing a room, and mautrix invites the bridge's owner into every portal room, so the operator's own account produces one every thirty seconds quite apart from their ghosts. And what it says is partly invented: presence in Matrix is not room-scoped, so the Sensor names a network by picking the lexicographically first bridged room the subject shares with it. An `inbound.presence.updated` claiming the operator is online *on WhatsApp* said so on the strength of which portal room sorted first. An event that is redundant, voluminous and partly fabricated has no shape worth designing; it has a reason not to exist. (The same arbitrariness can in principle reach a native Matrix contact — ADR 0009's bring-your-own-account path — if a real Matrix user is ever a member of a bridged portal room: `network::resolve` then returns that portal's protocol. A network ghost cannot be affected, because a bridge only puts its own ghosts in its own portals, so the set of answers has one element and the sort is not a choice. It matters more than a mislabelled field, because consent is looked up by `(subject, network)`: a decision the user made about that contact on Matrix would not govern an event labelled `whatsapp`. It is a separate defect from this one, filed as [#150](https://github.com/linagora/twalk/issues/150) rather than fixed here.)

Two things this ADR does not claim. The Sensor can refuse to *use* a consent row about the operator; it cannot remove one from the Gateway's store, and before ADR 0018 the user's own messages fed the Gateway's pending-contact projection, so an upgraded deployment can still hold such a row and offer the user a decision about their own ghost. "The owner never appears in the consent snapshot" has two producers and this is one of them; the Gateway half is [#149](https://github.com/linagora/twalk/issues/149), and until it lands the invariant does not hold everywhere. And the answer recorded here is per type: `sensor/tests/owner_is_never_a_contact.rs` reads `contracts/cloudevents/v1/` and fails on any type whose `subject` is a Matrix user ID and which has no recorded answer, so an eleventh type cannot be added without this question being asked again — which is the part of the work meant to outlive the ticket, because the alternative is a list that goes quietly stale and an invariant that quietly stops holding.
