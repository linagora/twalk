# Twalk perceives what involves other people, and a perimeter is a connection

Twalk observes **what happens between the user and other people, across the accounts they hold** — messaging first, then email, calendars and contacts. That is a frontier and not a slogan: an event that names nobody but the user needs none of this project's rules, so a build, an invoice or a feed goes to an agent directly and Twalk adds only a translation layer with no guarantee behind it. Where a third party is named, Twalk carries **the whole event and not a pulse**: an agent told merely that "something changed" must go and read the source itself, with its own credentials, which is the route by which every rule here stops applying — the hole [ADR 0032](0032-twalk-governs-what-an-agent-outside-it-may-see-and-do.md) named for WhatsApp, built on purpose. The principle is **carry richly, keep briefly**: an agent needs everything to decide well, and [ADR 0028](0028-a-contacts-words-live-apart-from-the-event-that-identifies-them.md) already separates what is carried from what is kept.

A **perimeter** is what a consent decision is scoped to, and it is a **connection** — one configured account, mailbox or calendar — of which a network is the *kind*. `network` was standing in for this and the substitution has already cost a defect: the Companion resolves a network's bridge with `bridges.find(row => row.network === card.network)`, first match wins, so granting `mattermost` would grant an employer's workspace and a personal one in a single gesture, and no message-flow event carries a `bridge_id` for the bus to tell them apart. Calendars and email do not create that problem; they make it impossible to ignore. So `connection` joins the envelope as the identity while `network` stays as the kind — two facts, two fields, because the interface, the icons and server-side subject filtering all want the kind while consent needs the instance. Existing decisions migrate by being attached to their network's single connection, which is **correct only because it is done now**: this deployment has exactly one of each, and the conversion stops being true the moment a second is added. The set of perimeters gets **one authority and a test that derives the others from it** rather than a list somebody must remember — the six network values are today hand-copied in twenty-one places across seventeen files and eight authorities, four of them SQL `CHECK` constraints, and nothing anywhere reads an enumeration out of a schema to compare it with anything.

A source that is not Matrix enters through a **collector**, of which the Sensor becomes the Matrix one — the role it always had, with one sense. Observation for such a source is **subscription and not filtering**: a collector receives only what it subscribed to, rather than receiving everything and discarding. The difference is measurable where a filter's would not be — a collector that never opened a session cannot have published from it — and it is as close to a structural property as anything without Matrix membership can be, which [ADR 0029](0029-a-conversation-outlives-its-room-but-the-room-stays-the-key.md) demanded when it refused thread-grain observation for exactly this reason. A person reached through two sources is **two subjects that the user may declare linked**, never merged by inference: ADR 0018 settled that shape for the owner's own identities — *an identity that cannot be confirmed as theirs stays a contact, because unknown is not the operator* — and the same rule applied to a third party matters more, because a wrong merge grants somebody else's consent.

**Email reuses the message types.** An email is a message: a person, a body, a time, a thread. The differences — a subject line, several recipients, threading by `Message-ID` — are fields and not a nature, and ADR 0005 already holds that a network outlives its transports, so `email` is one network whether it arrives by IMAP, JMAP or Gmail's API, and OAuth is how a connection authenticates rather than a protocol of collection. **A calendar does not.** Its events are the user's own, so a calendar event's `subject` is the **owner** and it carries **no `consent` extension at all**, exactly as `outbound.message.sent` does and for the same reason (ADR 0018, ADR 0021): the extension is a contact's decision and the user is not a contact. Participants are then third-party data *inside* an event about the user — the situation of a quoted excerpt, which ADR 0028 has already decided — so a revoked participant is reduced the way a revoked sender's body is, by the contract's own conditional rule. And a calendar gets **one type per kind of change** rather than one type with a `change` field, on ADR 0018's own argument that a consumer who forgets a filter fails silently while a consumer who never subscribes cannot be surprised.

> **Correction, [#280](https://github.com/linagora/twalk/issues/280).** The sentence above says a revoked participant is reduced *"by the contract's own conditional rule"*, meaning a JSON Schema `if`/`then` like the one that makes a revoked sender's reduced message checkable. That cannot hold for a calendar event, and the two halves of this ADR say why: the excerpt rule branches on the envelope's `consent` extension, and a calendar event carries none — its subject is the owner. There is no attribute on the event for a validator to branch on, and adding one would put a contact's decision on an event about the user, which is what this ADR refuses. So the rule is the contract's in words (`definitions/calendar-event.schema.json`, the `participants` description) and in a variant fixture, and what a validator checks is its shape: `participants_withheld`, the count of people withheld, the way a reduced attachment keeps `size_bytes`. The **decision** — a revoked participant is withheld whole, identity included, on the decision taken about that `mailto:` on the mail connection of the same account — is unchanged; what was wrong was the claim about the mechanism that enforces it.

Rationale: Hermes — the agent this deployment integrates with — **cannot detect anything by itself except by cron**; it reasons on what it is handed and is blind between handings. Twalk is what notices, which is a better account of why it exists than the list of capabilities it had before, and it is the account its owner gave: *the dynamic CloudEvents layer*. That layer is **independent of the agent** — the contract stays the contract, the webhook template is a rendering for one consumer and not the contract itself, and no consumer earns a privilege. The frontier was chosen over two alternatives. "Messaging" is what `CONTEXT.md` said and it is now false: a calendar movement is not messaging, and the project's own `README` has promised email, calendars, contacts, notes and RSS since before this ADR without a single schema, field or decision behind it. "Anything that can produce an event" was rejected because it explains nothing: the rules exist because other people are involved, and a frontier that admits a CI build admits something Twalk can only slow down. On the perimeter, widening `network` to hold `calendar` and `email` was the cheap option and loses on two counts — the word already lies twice in the contract (`bridge.status.changed` requires a `data.network` while declaring the extension optional; the three `persona.*` types carry a network *copied from their trigger*, not one they arrived on) — and widening an enumeration nobody compares across twenty-one copies guarantees they diverge.

The costs are accepted rather than argued away. **The contract roughly doubles**: ten types today, eleven with ADR 0028's words type, and calendar changes at one type per kind take it past fifteen. That price was paid deliberately twice before, for the ninth type and the eleventh, and the v1.0 freeze is ahead rather than behind — but it is a real cost and the next such decision should be weighed against a contract that is no longer small. **A perimeter that is a connection is a change to the consent key**, which means `consent.state.changed`, the store's `consent_decision_network` table and its view, and the Sensor's `HashMap<(String, Network), Consent>` — none of which is hard, all of which is load-bearing, and one of which is append-only by trigger. **Subscription is weaker than membership**, and this ADR says so rather than claiming otherwise: a Matrix membership is an event on a homeserver that the deployment cannot forge, while a collector's subscription is the collector's own honesty, trusted because it runs inside the deployment. **Two subjects for one person will feel wrong before it feels right** — revoking somebody on WhatsApp will not revoke them by email, and the user will discover that at the moment it matters unless the interface says so first. And a mailing list is a non-human in the person namespace, the third instance of ADR 0026's class after bridge bots and Telegram's broadcast channels, which suggests that class is not a series of accidents but a property of bridging anything.

**Amendment, 2026-09-24 ([#342](https://github.com/linagora/twalk/issues/342)):** a connection is a perimeter **and** a credential. Consent is scoped to a connection because that is the account a contact reached the owner through; what this adds is that the way the deployment proves itself to that account belongs to the connection too, and not to the process. An OIDC grant, a `Basic` username and password, a Cozy OAuth registration — one connection, one credential, and a process holds one connection's worth of it. See [ADR 0038](0038-an-oidc-grant-is-the-users-identity-and-a-jmap-submission-their-device.md)'s amendment for why that makes a second connection a second collector rather than a second secret in the same one.
