# The drafting agent is graded by what it can reach, not by how clever it may be

The agent that drafts a reply may think for as many turns as it needs, read the public web, and load any skill it judges relevant. What it may **reach** is graded, and the grades are about the blast radius of a capability rather than about the agent's freedom: **public reads** are open, the **owner's own data** is reachable only through narrow functions the deployment governs and journals, and **arbitrary execution on the host** — a shell, a file, a process — is refused.

Rationale: the drafting lane is the one place in this project where the *input is written by a stranger*. A contact's mail is text somebody outside the deployment composed, handed to a model that then decides what to do next; [ADR 0032](0032-hermes-runs-outside-the-deployment.md) already puts that model on a machine Twalk may not own. So the question is not whether the agent should be capable — a draft written blind is the defect [#363](https://github.com/linagora/twalk/issues/363) exists for, where a reply accepted a meeting slot with nothing having read the calendar — but which capabilities a stranger's paragraph could turn against the owner. Those are not the same for every tool, and treating them the same is how a system ends up either useless or dangerous.

**Public reads are open, because their failure is a bad draft and a bad draft is caught.** Web search and fetch are already on that lane, and stay. A poisoned page can mislead the draft; it cannot take anything, and every word the agent produces is a suggestion a human reads before it leaves ([ADR 0022](0022-the-approval-api-lives-on-the-companion-gateway.md)). The approval is the control, not the absence of the capability. What the agent must never do is present what it read as the owner's own knowledge: a fact from the web goes in the draft as something the owner can check, and [ADR 0019](0019-a-persona-discloses-itself-to-the-contact.md)'s disclosure already says a persona wrote it.

**The owner's own data is reachable only through one function per read.** Not a shell that runs a script, not a filesystem tool pointed at a directory, not an HTTP tool that could be aimed at any URL: a named function, whose arguments are the read's own parameters, signed to the Companion Gateway with the answers' secret, capped where the read has a natural cap, refused on a connection that is not connected, and recorded in the owner's journal whether it was served or refused ([#206](https://github.com/linagora/twalk/issues/206), [#281](https://github.com/linagora/twalk/issues/281), [#355](https://github.com/linagora/twalk/issues/355)). Today that is two functions — when the owner is busy, and what one of their events carries. A third is a ticket, an argument, and a journal of its own, which is the cost this grade is meant to impose.

**A skill is instructions, not a capability, so loading one grants nothing.** The route may name the skills it wants injected, and the lane may hold the tools that let the agent find and read others itself. A skill that tells the agent *never name a time you have not read* is worth more than a rule in a prompt nobody re-reads, and a skill that teaches a workflow costs the deployment nothing but tokens. What a skill cannot do is widen the grade above it: `skills/twalk-calendar` says how to use the two governed reads and would say the same if the agent had no way to make them.

**Arbitrary execution is refused, and this was measured rather than assumed.** On 2026-09-24 the reference deployment's drafting lane was given a terminal for one afternoon, to prove [#363](https://github.com/linagora/twalk/issues/363)'s loop end to end. It worked — three slots, each really free — and the agent's first two commands, unprompted and with no bad intent, were a `cat` of a `.env` file (it had the grace to `sed` the secret out of its own output) and a read of `SOUL.md`. Those are the gestures of an agent orienting itself on a new machine. They are also, word for word, what a well-turned paragraph in an email could make it do to something else, and there is no prompt that reliably prevents it: the capability is the exposure. So the shell was withdrawn the same minute and replaced by the narrow tool [#368](https://github.com/linagora/twalk/issues/368) builds.

Three alternatives were weighed and rejected. **No capabilities at all** — the one-shot drafter this project shipped until #363 — produces the failure the owner actually met: an agent that cannot look up anything invents, and invents fluently, which is worse than an agent that says it could not check. **A shell, governed by prompt** — telling the agent which commands it may run — puts the security boundary inside the model, on the far side of the seam, where a stranger's text is also being read; it is the boundary this project refuses everywhere else. **One wide tool with an allowlist of URLs** — an HTTP tool restricted to the Gateway's origin — is narrower than a shell and still wrong in kind: it would reach every route the Gateway serves, including the ones that hold the owner's approvals, and its arguments would be a URL rather than a read's parameters, so the journal could not say what was asked without parsing it back.

The costs are real and are accepted. A function per read is more work than a shell, and every new capability has to be built, named, journalled and documented rather than granted. The grades will occasionally be wrong in the restrictive direction — an agent will want something reasonable it cannot reach, and the answer will be a ticket rather than a flag. A public read can still be poisoned, and the only thing standing between that and the owner is the approval, which is exactly where this project has always put it. And the journal only helps if somebody reads it: what makes autonomy safe to want is that the approval screen shows what the draft **did** before it wrote — the reads it made, the question it asked — which is [#367](https://github.com/linagora/twalk/issues/367)'s work and belongs with this decision rather than after it.
