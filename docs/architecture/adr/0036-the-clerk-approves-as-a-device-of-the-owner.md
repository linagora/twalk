# The clerk approves as a device of the owner

A ✅ the owner puts on a post in `approbations`, or a reply in its thread, becomes **the** approval — the Companion Gateway's, through `POST /api/approvals`, the same call the Companion's approval screen makes — and the clerk makes that call **as a device of the owner** ([#284](https://github.com/linagora/twalk/issues/284)). It signs in the way a phone or a browser tab does ([#52](https://github.com/linagora/twalk/issues/52)): once, with a Matrix OpenID token an operator mints at the terminal (`provision-clerk-device.sh`), under a device name the owner will recognise, `Buzz`. From then on it holds what such a device holds and nothing more — one **refresh token**, in a file it owns and rewrites on every `POST /api/session/refresh`, since the Gateway rotates both tokens at each refresh; and one **device token**, alive for fifteen minutes in the clerk's memory and written nowhere. It is listed on the dashboard beside the owner's other devices and revoked there like any of them, and the approval it makes is the owner's: `approved_by` is the owner, through that device, because the Gateway stamps the owner and never a device on that row. Buzz remains a **surface and never an authority** ([ADR 0032](0032-twalk-governs-what-an-agent-outside-it-may-see-and-do.md)): the relay records the gesture, the Gateway records the decision, and the clerk carries the one to the other. The clerk still holds no service token — the credential that opens the consent snapshot, the list of every contact — and no credential the Gateway would take for anyone but the owner's own device.

Rationale: the question was what credential a process may hold to approve in the owner's name, and the device is the answer the Gateway already had. [ADR 0011](0011-gateway-authenticates-with-matrix-openid.md) gave the Gateway exactly two classes of caller: the owner's devices, each signed in by a Matrix OpenID token the homeserver vouches for and each revocable from the dashboard; and two services, the Sensor and the persona runtime, holding one service token that opens the two reads a service needs and nothing else. An approval is a human act — [ADR 0022](0022-the-approval-api-lives-on-the-companion-gateway.md) moved the endpoint onto the Gateway so that the `approval` table would be the one record of what Twalk sent in the user's name — and the human who makes it on Buzz is the owner, so the caller should be what the owner's callers are. Two alternatives were weighed and rejected. **A second service token**, minted for the clerk and mapped to `POST /api/approvals`, would be a second class of credential on the Gateway: a machine token that opens a *write* rather than a read, with `approved_by` fixed by configuration rather than by who signed in — so the audit row would say "the owner" on the strength of an `.env` line — and with no place on the dashboard where the owner sees it exists or takes it away; and it would put the clerk one configuration mistake from holding the token that opens the consent snapshot, since the two would be the same kind of thing set the same way. **NIP-98 on the Gateway** — the Gateway verifying the owner's own Nostr signature on the approval request, so that the ✅ itself is the credential — would be elegant and was the more tempting: it would need no session and no file. It was refused because it puts a Nostr verifier on the Gateway's write path for the sake of one client, and because it makes the Gateway learn a second identity for the owner, a Nostr public key, beside the Matrix identity it already verifies — two owners' names for one owner, and a question the whole authentication model would then have to answer ("which one is the owner when they disagree?") that today does not exist. A device costs the Gateway nothing new: no route changes, no verifier is added, and the guard that takes a device token on every `/api` route is the guard the clerk's calls pass through.

The costs are accepted rather than argued away. **A thirty-day credential on a process, at rest**: the refresh token is a file on the host, mode 0600, and whoever reads it approves as the owner for thirty days or until the device is revoked — it is in the security model's credential table beside the others, and it is the first credential in this deployment that is at once a *human's* right and a *machine's* possession. The mitigation is the one [ADR 0025](0025-twalk-acts-as-the-user-through-a-device-of-their-account.md) accepted for the Sensor's Matrix device and for the same reason: it is **revocable like a phone**, from the dashboard, with no shell and no Twalk involvement, and the clerk answers the next ✅ in the thread naming the revocation rather than failing silently. What the token grants is also narrower than a device token sounds: the clerk's code makes one call with it, `POST /api/approvals`, and reads one listing, `GET /api/devices`, in the operator's script — but the Gateway does not enforce that narrowing, and a device token opens every `/api` route, consent included, which is why the file is the thing to protect. **An operator route with a password at the terminal**: the OpenID token can only be minted by the owner's own Matrix login, so the script asks for the owner's password once, on the terminal or from a file, and logs the Matrix device it made out at the end — the same shape and the same discomfort as `provision-owner-device.sh`, and the same argument that the alternative, the Companion doing it from the browser, is a later lot's. **A session that dies unused**: a clerk down for thirty days comes back with a dead refresh token and no way to renew it, and says so in the thread and the log rather than looping; the script run again restores one `Buzz`, revoking every other unrevoked device of that name, because a device nobody knows exists is one nobody revokes ([#227](https://github.com/linagora/twalk/issues/227)). And **the session file is the one thing the clerk writes to disk**: [ADR 0035](0035-the-clerk-is-a-projection-of-the-relay-and-holds-no-state.md) stands — the clerk keeps no state, and what it already decided it finds on the relay — because a credential is not state: it records nothing about a suggestion, a post or a decision, and losing it loses no fact, only the right to record one until the operator signs the device in again.
