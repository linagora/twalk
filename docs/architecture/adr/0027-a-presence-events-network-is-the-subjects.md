# A presence event's network is the subject's, and an unattributable subject is not published

An `inbound.presence.updated` event's `network` names the network **the subject is on**, derived from something that identifies them, and never from an ordering over the rooms they happen to share with the Sensor. In precedence order: a **ghost localpart** (`@whatsapp_<id>`, `@signal_<id>`) is the subject's own identifier on that network and answers outright, whatever rooms they are in; failing that, sharing a room **no bridge marked** is positive evidence that the subject is a Matrix account in its own right — a bridge puts only its own ghosts in only its own portals — so the answer is `matrix` (ADR 0009) and their membership of somebody's portal is an invitation rather than an identity; failing that, the single network every portal they share resolves to, which is how a puppet whose bridge does not use a `<network>_` localpart template is still attributed. When none of those answers — portals of two networks holding a subject that is a ghost of neither and that shares no unbridged room — **the event is not published at all**, at `warn` and counted as `twalk_sensor_events_dropped_total{reason="unattributable_subject"}`. The room named in `source` is then the first, in room-id order, of the rooms that resolve to the network already decided: an ordering may break a tie between rooms that agree, and may not decide anything a consumer reads. Where no shared room agrees — reachable in one shape only, a ghost of one bridge that shares nothing but another bridge's portals, which is a misconfigured deployment — the event still publishes, naming the first shared room and warning about the disagreement. The network stays the subject's, `source` names a room they really share (which is all the contract claims of it now that the field's description says so), and dropping a person for a misconfiguration would be the worse answer. `network::subject_network` is the whole policy, pure and unit-tested; `network::resolve` is untouched and still answers for a *room's* traffic, where a portal rightly wins over the native fallback — the inversion here is deliberate and applies to subjects only.

Rationale: presence in Matrix is not room-scoped. It arrives as an EDU about an account, with no room attached, and the contract's `source` is a portal room URI — so the Sensor had to name a room, and it named the lexicographically first joined room the subject shared with it that resolved to a bridged network. ADR 0021 already recorded that as a fabrication ("an `inbound.presence.updated` claiming the operator is online *on WhatsApp* said so on the strength of which portal room sorted first") and filed it as [#150](https://github.com/linagora/twalk/issues/150) rather than fixing it. For a ghost the sort chose nothing, because the two resolution paths agreed over a one-element set of answers. For a **native Matrix contact** — ADR 0009's bring-your-own-account path — it chose everything: their own rooms carry no `m.bridge` state, so they normally take the `matrix` fallback, but a single membership of a bridged portal (invited by hand from a Matrix client, or a bridge running in relay mode) made `resolve` read *that* room's `protocol.id`, and the loop stopped at the first such room in id order.

What makes it more than a mislabelled field is that **consent is keyed on `(subject, network)`**. A decision the user took about that person on Matrix does not govern an event labelled `whatsapp`, and vice versa: the consent model reads a row that is not the one the user wrote. That is a different class of defect from a cosmetic label, and it is in the part of the system whose only job is to be trustworthy. How reachable it is today is narrow and worth stating: no Twalk code path puts a real Matrix user into a mautrix portal. Narrow is the right word for it, not impossible.

The shape of the answer was the open question, and "one event per network" was rejected on the contract rather than on taste. The deterministic id is `sha256(matrix_user_id + ':' + presence + ':' + receipt_timestamp_ms)` — there is no network in the natural key — so N events for one transition would share one id, and JetStream's `Nats-Msg-Id` dedup would store exactly one of them, arbitrarily chosen. Making the key network-scoped is a breaking change to `id` on a v1 type. And it would be a second fabrication anyway: a Matrix presence transition says an *account* came online, not that a person is available on WhatsApp *and* on Matrix, so fanning it out would multiply the invention instead of removing it. That leaves one event or none, and the criterion for which is whether anything identifies the subject. "No network at all" is not expressible either — `network` is required on every message-flow event (CONTEXT.md), and making it optional for one type would tell every consumer that the extension it filters on may be missing. So the unattributable case is an absence of the event, which is what "a subject the Sensor cannot attribute to a network is not published under a guessed one" means in practice.

The audit asked for by the ticket: **presence is the only event type that resolved its network this way.** A message and a reaction happen *in* a room, so the room they arrived in answers for them and there is nothing to choose; `resolve_network` is called once, on that room. The outbound types take the same room. `consent.state.changed` and `bridge.status.changed` are the Gateway's and carry the network of the decision or the bridge. Presence was the one type whose subject had no room of its own, which is exactly why it grew a sort.

One limitation stays, and it is the reason the second rule is evidence and not a guess. A native Matrix contact who shares **only** a bridged portal with the Sensor and no unbridged room is still attributed to that portal's network: everything the Sensor can observe about them says `whatsapp`, and it has no way to ask whether a localpart belongs to an appservice namespace (the registration files are the homeserver's, not the Sensor's). What changed is that the answer no longer depends on which room sorted first, that the case the ticket describes — a real Matrix user with rooms of their own *and* a portal — now answers `matrix`, and that two portals of different networks produce a warning and a counter instead of a coin toss.
