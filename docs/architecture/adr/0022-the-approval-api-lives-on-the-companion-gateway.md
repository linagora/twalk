# The approval API lives on the Companion Gateway, not on the Hermes runtime

`POST /api/approvals` is served by the Companion Gateway, which reads the suggestion and its trigger from the bus, checks the suggestion's `expires_at`, checks the trigger's observed consent label, checks the sender's **current** consent state in its own journal, and publishes `persona.reply.approved.v1` itself. The Hermes runtime keeps no approval endpoint: it starts and supervises personas and does nothing else with a human decision. This overrides spec #19, which placed `POST /v1/approvals` on the runtime (loopback-only) and — after the design review recorded on #24 — had the runtime call the Gateway's `GET /api/consent/effective` before publishing, refusing the approval if the Gateway could not be reached. The event's `source` is still `hermes://<domain>/personas/<persona id>`: the contract's `source` identifies the persona whose suggestion was approved, not the process that published the approval, and the schema's description — which said the event is emitted by Hermes — was corrected in the same pull request rather than left contradicting its producer. There is no outbox on this path: an approval publishes inside its own request or it is refused, which is the opposite of how a consent decision is published and is deliberate (`companion-gateway/src/approval.rs`).

Rationale: `CONTEXT.md` defines an approval as "refused if the sender's consent is no longer `granted` **at that moment**", and names the Companion Gateway the single writer of consent state (ADR 0006). Asking that question from another process turns a local read into a network call, and a network call has a failure mode the local read does not: an authority that refuses and an authority that cannot be reached arrive at the caller as one signal unless somebody is careful, which is precisely what #116 (`bridge_unreachable` for a bridge that answered) and #141 (a `401` meaning both an expired session and a rejected third-party token) cost this project. #24's own comment anticipates it and mitigates it — fail closed when the Gateway is unreachable — which is the right mitigation for a problem that need not exist. The Gateway is also already the approval's only caller: an approval is a human act from the Companion, which holds a session with the Gateway, so the runtime route is Companion → Gateway → loopback runtime → bus, one hop and one failure mode longer to reach a component whose only advantage is that a document said so. The case for the runtime is real and is the reason this is an ADR rather than a footnote: Hermes owns the `persona.*` domain everywhere else, the contract's own prose attributed this event to it, keeping a human decision out of the component that serves the browser is a defensible separation, and a runtime that owns both the suggestion's production and its approval could one day enforce properties across the pair that a second publisher cannot. Two things decided against it. The consent check is not incidental to an approval, it is the definition of one, and it belongs where the state is. And the Gateway already has what the act needs — the journal, a bus connection, an authenticated owner session, and the deterministic-id publishing discipline the outbox established — while the runtime would have needed a second copy of all of it. Two known costs are accepted rather than hidden: the Gateway now publishes a second event family (it was already the sole producer of `bridge.status.changed`), and the approved reply carries no `target.reply_to_event_id`, so it lands in the portal room without being a native Matrix reply — the contract's inbound event carries no Matrix event ID of its own to thread under, and inventing one would be worse than the gap. The decision is reversible: the runtime can take the endpoint back by reading the same three things, and this record is the argument to reopen.
