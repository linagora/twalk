# The Companion's cryptographic bootstrap runs in the browser

The Companion generates the user's cross-signing keys and recovery key in the browser, with matrix-js-sdk's Rust WebAssembly crypto stack, and the Companion Gateway never sees any of it. The crypto store is persisted in IndexedDB and left unencrypted, because any key protecting it would live in the same browser storage. Losing that store is a normal event, not an error: on iOS, Safari deletes it after seven days without interaction unless the Companion is installed to the home screen, so "my store is gone, let me re-enter my recovery key" is a designed path with its own screens, and installation is offered on iOS rather than imposed. Two tabs sharing the store would corrupt it, so one tab holds a lock and the others say so. A browser that cannot do the job — iOS Lockdown Mode, which disables IndexedDB, or a page outside a secure context — is detected and explained before onboarding starts, never mid-flow.

Rationale: this is the only path. matrix-js-sdk removed its libolm backend in 37.0.0, and the recovery key is generated by a client-side callback by construction, so no server-side option exists even if we wanted one — which ADR 0011 says we do not, since screen 2 promises the user that Twalk never sees that key. The cost is weight and fragility, both bounded: the login screens carry about 230 KB compressed, the 1.3 MB of stripped and brotli-compressed WebAssembly loads only on the bootstrap screens, and no cross-origin isolation is required. The unencrypted store was weighed against a passphrase the user would retype at every visit, and rejected for a configuration surface consulted in passing; it is recorded in the security model rather than hidden. What remains genuinely unverifiable by automation — Safari's eviction, the installed-app exemption, Lockdown Mode — is checked by hand on a real device, as an acceptance criterion.
