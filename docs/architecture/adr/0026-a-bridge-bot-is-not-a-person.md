# A bridge's own bot is not a person, and nothing is published about it

A bridge materialises two kinds of Matrix account, and until now the Sensor knew only one of them. A **ghost** stands in for somebody on the other network, and every word of the consent model applies to it. The **bot** — `@whatsappbot:…`, `@signalbot:…`, each bridge's own `appservice.bot.username` — is the appservice's own service identity: it creates portals, puppets ghosts, invites the user, and is a member of every portal room of its network. It is neither the owner nor a contact, so nothing is published about it on any event type: not its presence, not a message it posts into a portal room, not a reaction it adds, and no `consent` decision about it enters the Sensor's cache, from the Companion Gateway's snapshot or the `consent.state.changed` stream alike. Which accounts those are is **handed over by the deployment** (`SENSOR_BRIDGE_BOTS`, each configured bridge's `appservice.bot.username` as a full Matrix ID — **not** its `sender_localpart`, which is a different account entirely: see below), on exactly the terms ADR 0018 established for the operator's identities: an exact match against what was confirmed, never a prefix, a pattern or a display name. An account the deployment did not name stays a contact and is published as one. The three things that make this observable rather than a silence are all deliberate: the set is logged at startup, its absence is logged as the defect it is, and every dropped event is counted (`twalk_sensor_events_dropped_total{reason="bridge_bot"}`), so a flat zero on a deployment that runs bridges reads as "this variable names an account that does not exist" instead of as "there is nothing to drop". `sensor/tests/bridge_bots_are_not_contacts.rs` enumerates the contract the way `owner_is_never_a_contact.rs` does, so an eleventh type whose subject is a Matrix user ID cannot be added without somebody answering what it does about a bot.

Rationale: ADR 0021 removed the owner's presence for the right reason and on a false premise. The owner's presence *was* redundant and partly fabricated, and removing it was correct — but it was never the volume. Measured on the reference deployment the moment #147 made the rest visible: `@whatsappbot` 680 events, `@signalbot` 470, the owner 34. Two service accounts were 1,150 of 1,216, and they still are, two a minute, for as long as the deployment runs. The volume is the least of it. These events travel through the **contact** machinery: a bot reaching `inbound.presence.updated` had been resolved as a subject, looked up in the consent cache, labelled with whatever applied — and `ConsentCache::state` falls back to the *network's* default, so on an ordinary deployment that grants a whole network the answer is `granted`, not `pending` — and given a `contact` object with its display name. So a deployment's consent state can hold rows about `@whatsappbot`, and a user can be offered a decision about a robot; anything built on the stream later ("who has been active recently") answers: two robots. That is ADR 0021's problem with a third non-person in it, and #149 is the Gateway's half for both.

The set is configuration, and the two alternatives were rejected for one reason read twice. **Reusing `SENSOR_ALLOWED_INVITERS` minus the operator's identities** needs no new variable and is wrong: that list answers "whose invitation do I honour?", an operator may legitimately put a second account of their own on it, and that person's presence would then vanish from the bus as a side effect of an unrelated setting. **Reading the portal's own `m.bridge` marker**, whose `bridgebot` field names the bot, needs no configuration at all and would fix the reference deployment without anybody editing a file — but it is room state, so it is attacker-influenced: a member with the power to send state in a room the Sensor observes could name a contact as that room's `bridgebot` and delete them from the stream. Requiring the marker to have been *sent by* the account it names closes that hole (a sender cannot be forged, so the only identity anyone can suppress that way is their own), and it was the close call here; what decided it is that the rule would then rest on a mautrix behaviour Twalk does not control, and the failure mode of being wrong about it is the silent one — the bots are never recognised and the defect ships looking fixed. The cost of choosing configuration is stated rather than hidden: the reference deployment keeps publishing bot presence until one line of `.env` names the two accounts it already names in `SENSOR_ALLOWED_INVITERS`.

What the configuration is therefore not is the last word. Unlike the operator's ghosts, which ADR 0018 showed are *not derivable at all*, a bridge's bot has an authoritative source: each bridge's provisioning API answers its own in `GET /whoami` as `bridge_bot` — `sensor/tests/bridges_deployment.rs` already asserts that field against both real bridges — and the Companion Gateway already holds every bridge's secret and already acts with its appservice token (ADR 0024). Serving the set from there would remove the one line of `.env`, and `BridgeBots::new` is the seam it plugs into. What it would not remove is the need for the set to exist as a set: the Sensor has no provisioning credential, and it must keep behaving correctly when the Gateway is unreachable, which is the same reason ADR 0010 gives the consent snapshot a cold-start path.

The direction of the safe failure is the opposite of this project's usual one, and that is the load-bearing part rather than an aside. Everywhere else in Twalk doubt goes to restraint — an unattributable sender is skipped, an unknown quoted author is withheld, `pending` is not a weaker yes. Here restraint is the dangerous choice: suppressing a contact because something about them resembles a bot makes a real person disappear from the bus in silence, which no consumer can detect, no operator can diagnose, and no label records. So unknown is not a bot, and the test proves the two halves separately — the bot dropped, and a contact in the same room still published — because a fix that dropped both would pass any test that only looked for the absence.

Two things this ADR does not claim. A bot's **excerpt** takes the ordinary rule and not this inversion: when a bridge bot wrote the message somebody replied to or reacted to, the excerpt is withheld (`QuotedAuthor::Unknown`) rather than published, because there is no decision about a robot to consult and withholding costs a line of service output instead of a person's visibility — the event itself still publishes, with its relation intact. And the Sensor can only refuse to *use* a consent row about a bot; removing one from the Gateway's store is [#149](https://github.com/linagora/twalk/issues/149)'s half, and until it lands "a bridge bot never appears in the consent snapshot" does not hold everywhere.

One correction is recorded here because getting it wrong has already cost this project a defect, and this ADR's first draft got it wrong again. A bridge's bot and its appservice's `sender_localpart` are **not the same account.** `sender_localpart` is the identity an appservice token acts as when it names no user; on a deployment whose registrations are generated it is a random localpart — measured on the reference deployment as `@jaay9HZczkCQNHiIzolLOrvm99Cby90B`, joined to **zero** rooms — while the bot that is in every portal and produced 680 of that deployment's presence events is `@whatsappbot`, from `appservice.bot.username` in `bridges/mautrix-whatsapp/config.yaml`. [ADR 0024](0024-a-portal-room-is-observed-by-invitation-per-conversation.md) asserted the same equivalence, the portal register asked the wrong account for it, and the deployment reported 0 of 32 conversations while every component called itself healthy ([#171](https://github.com/linagora/twalk/issues/171)). So the rule is the same one ADR 0018 reached about the owner's ghosts, for the same reason: the account is **named by the deployment from the bridge's own configuration**, never derived from a convention the reader assumes — and `sender_localpart` is the convention that looks right and is not.
