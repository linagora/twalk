# The user's device credential goes from browser to Sensor and is never relayed

The device [ADR 0025](0025-twalk-acts-as-the-user-through-a-device-of-their-account.md) requires is **created in the browser** during onboarding, as an ordinary login on the user's own account named `twalk`, and its access token reaches the Sensor as an **Olm-encrypted to-device message addressed to the Sensor's device** — so the Companion Gateway is not in the path at all and ADR 0025's sentence stays literally true rather than being amended. The Sensor accepts such a message **only** when it arrives decrypted and its `EncryptionInfo` names the device the deployment expects; a to-device event that arrives in the clear, or undecryptable, is discarded and counted, because an unencrypted one is either an attacker's or a bug and the two deserve the same answer. The handover is **acknowledged on the bus, not assumed from the send**: the Companion reports success when the Sensor says it holds the credential, never when the send resolves, because the send resolving means nothing (see below). The device is **write-only**: it joins portal rooms and posts approved replies, it never reads history, and therefore it needs neither cross-signing nor a recovery key — which removes from the critical path the one step ADR 0025 called "the hard part" and which no automation may shortcut. The Sensor keeps it beside its own session and **never confuses the two**: one identity observes and one identity acts, and the observing one keeps every property ADR 0024 rests on. The device appears in the user's device list under a name they will recognise, and revoking it from any Matrix client stops Twalk replying without touching anything else.

Rationale: the shape was chosen after measuring the deployment rather than from the ADR's own description of the problem, and three measurements moved it. **The bridges accept unverified devices** — all four configured bridges carry `verification_levels.send: unverified`, so a message from a device nobody cross-signed is relayed to the network exactly like any other; cross-signing is what a device needs to *read* encrypted history, and this one reads nothing. **A Matrix access token of the user's already transits the Gateway today** — `docs/architecture/security-model.md` records it as a parameter of `POST /api/bootstrap/rooms` that "is gone when the call returns", asserted by `companion-gateway/tests/bootstrap.rs` — so the honest reading of ADR 0011 is that the Gateway stores no Matrix token, not that none passes by. That made a Gateway relay defensible and it is still rejected, for a reason the precedent itself supplies: what transits today is a token the browser already had and the Gateway drops within one call, whereas this one is **long-lived and destined to be kept**, so relaying it would put a durable credential of the user's account into request bodies and logs for the lifetime of the deployment. To-device delivery is not a mitigation bolted onto that, it is the absence of the problem: the Gateway never receives the bytes, and *"a mechanism nobody can forget beats a documented rule"* is this project's own phrasing ([ADR 0028](0028-a-contacts-words-live-apart-from-the-event-that-identifies-them.md)). The alternative of an operator script prompting for the password on the host honours every constraint and loses on product shape alone — it is an installation step rather than a screen — and it stays the documented fallback for a deployment whose Companion cannot reach the Sensor's device. Both sides of the mechanism were verified in the installed code rather than in documentation: `MatrixClient.encryptAndSendToDevice` performs no verification or cross-signing check and takes an arbitrary user id, and matrix-sdk surfaces decrypted **custom** to-device events in full, with a test of its own that sends a custom type from an unverified cross-user device and asserts the content survives.

The costs are accepted rather than argued away, and the first is a trap that would otherwise have been found in production. **A send to an untracked user is a silent no-op**: `encryptToDeviceMessages` skips a device the Olm machine does not know with a `logger.warn`, the batch goes out empty, and the promise resolves successfully — matrix-js-sdk's own comment concedes that "the batch mechanism removes all possibility to get error feedbacks". A user becomes tracked only through membership of a shared **encrypted room**, and at onboarding the user's account is joined to none with the Sensor in it — it is *invited* to portal rooms and has never accepted, which is the very defect being fixed. **That prerequisite is necessary and not sufficient, which this ADR got wrong and [#226](https://github.com/linagora/twalk/issues/226) corrected by building it**: in the installed matrix-js-sdk, `OlmMachine.updateTrackedUsers` is reached only from `RoomEncryptor`, which only `RustCrypto.onCryptoEvent` constructs, which the SDK calls from exactly one place — its sync loop — and the Companion runs none. So membership alone leaves the send as silently empty as no room at all, and the room must be accompanied by enough sync for the crypto machine to learn of it. The sentence above described a property of Matrix; what governs is a property of this client. And the positive acknowledgement is what makes the whole class visible instead of silent: without it, a deployment would report a device it does not have, and every variant of this mistake — no room, a room nobody synced, a device that never uploaded keys — would look identical to success. **The trust requirement is one configuration line from closing**: the default `TrustRequirement::Untrusted` is what lets an unverified device's custom to-device event decrypt at all, and anyone hardening the Sensor to `CrossSigned` later breaks this channel into undecryptable events rather than into an error — it is recorded here so that the next person to touch decryption settings reads why. **A second long-lived credential now sits on the Sensor's volume**, which `security-model.md` already states is not encrypted, so the exposure of that volume grows from the Sensor's own account to the user's; it is bounded by being a device among the user's devices and revocable without Twalk, which is ADR 0025's own mitigation and no stronger here. And **a write-only device cannot confirm its own writes**: it posts into a room whose history it will not read, so the question #216 asks — did this actually reach the contact — is not one this device can answer, and must be answered from the Sensor's own observation of the room it is already in.
