# The bus keeps ninety days and two gigabytes and no more

The `twalk` JetStream stream keeps an event for **ninety days** and holds **two GiB** at most, discarding the oldest when either limit is reached; its blocks are compressed (`s2`), and it remembers a `Nats-Msg-Id` for **a day** rather than the two minutes it did. File storage, one replica, no count ceiling. Every field of the stream's configuration is named in one place, `sensor/src/bus.rs`, so a reader sees the policy without knowing NATS's defaults — and the three values are the operator's to set (`SENSOR_BUS_MAX_AGE_DAYS`, `SENSOR_BUS_MAX_BYTES`, `SENSOR_BUS_DUPLICATE_WINDOW_SECONDS`), with the decided ones as defaults and a value NATS would read as "no limit" refused at startup by name. The **Sensor owns the policy**: at startup it creates the stream with it, or **updates an existing stream in place** and says field by field what changed, `old → new`; an update the bus refuses — JetStream cannot change a stream's storage, retention or name on a live stream — is an `error` naming the field, the bus's own reason and the operator's two options, and the Sensor runs on the stream's existing policy. Twalk **never deletes or recreates a stream**: expired events are gone for good, and taking them away is the operator's act and not a restart's. The other four components that create the stream when none exists keep doing so with a bare configuration, so a deployment that starts the Companion Gateway first still works, and the Sensor reconciles it when it comes up. This ADR says out loud what the stream's `..Default::default()` never did: **the bus holds contacts' messages**. Portal rooms are end-to-end encrypted and Synapse holds only ciphertext, so the bus is the only place in the deployment where the plaintext of other people's words exists at rest, and how long it keeps them is a **personal-data decision** before it is a disk one — a stream with no age is an archive of other people's conversations that nobody chose to keep, in a product whose promise is that no message leaves the user's infrastructure without consent. The decision was the operator's, taken on 2026-09-19 with the measurements below in hand ([#174](https://github.com/linagora/twalk/issues/174)).

Rationale: read off the reference deployment's own store (`meta.inf`) that day, the stream had `max_age 0`, `max_bytes -1`, `compression none` and `duplicate_window 120s` — nothing ever expiring, no ceiling, and events stored raw — and held 2.2 MB across some 1,530 events twenty-seven hours after it was created, about 2 MB a day, of which 95% was the presence defect [#152](https://github.com/linagora/twalk/issues/152) since removed; a real account's traffic is nearer 1 MB a day. Two MB a day is not the problem. A self-hosted appliance whose store has no ceiling is: that host reached 100% disk three times on 2026-09-18, and a deployment that fills a user's disk because its event log has no policy is a defect of design and not of capacity. **Ninety days** is long enough that a replay means something and short enough that the bus does not silently become an archive: the consent screen can name a contact only from a name it reads on the bus, nothing stores that name by design, and a message-level history exists nowhere else — no projection holds one — so this is the span in which the product can still say who wrote and when; it is also the number [ADR 0028](0028-a-contacts-words-live-apart-from-the-event-that-identifies-them.md) already assumed for the identity half of an event, made real. **Two GiB** is not the working limit and is not meant to be — ninety days of real traffic is nearer 90 MB — it exists so that the user's disk is never the thing that gives way, and `discard old` rather than `discard new` because a bus that refuses a new message to keep an old one is a bus that silences a conversation to preserve a stale one, which is the wrong way round for everything downstream. **`s2`** because CloudEvents JSON compresses several-fold, no consumer is affected, and it costs nothing to decide. And the **duplicate window is a correctness fix** and not a storage one: the Sensor publishes with a `Nats-Msg-Id` derived from the event's content so that a republication of the same Matrix event is dropped by the bus, and a Sensor restart re-syncs from Matrix and republishes — the live logs show it reprocessing sync responses — so any event republished more than two minutes after the first landed **twice**, with two stream sequences, and every consumer saw it twice: a persona triggered twice on one message, a contact counted twice. Two minutes protected against a retry in flight and nothing else, which is not what the deduplication was for; a day is longer than any re-sync an ordinary restart produces. The policy is reconciled **in place** rather than by recreating the stream because a recreation is a purge under another name, and applying it at the Sensor's startup rather than by an operator's `nats` command because a policy that exists only in a runbook is one a deployment upgraded across this ticket never gets; the reconciliation is *loud* on both paths — each changed field at `info`, a refusal at `error` with the options — because the one failure this project has shipped repeatedly is a silence.

The costs are accepted rather than argued away. **A replay is now ninety days deep and no deeper**, and every consumer that rebuilds itself from the stream inherits the bound. The Companion Gateway's pending-contact projection is created with `DeliverPolicy::All` so that a Gateway installed after weeks of traffic still knows who wrote; installed fresh after ninety days it **cannot rebuild a contact list older than that** — a contact who wrote once, ninety-one days ago, and was never decided on is not pending on a fresh Gateway and is not anywhere else either, since the projection is the only thing that held the sighting. The consent journal is unaffected: it is the Gateway's own SQLite, the bus carries a copy of each decision and never the record, and the Sensor's cache recovers from the snapshot ([ADR 0010](0010-consent-snapshot-then-deltas.md)) and not from the stream. The **Hermes runtime is the consumer this bound genuinely hurts**: it learns which personas the user activated by replaying `consent.state.changed` from the beginning of the stream and reads no snapshot, on [ADR 0013](0013-persona-activation-is-a-consent-decision.md)'s arithmetic that persona decisions are a handful over a deployment's life — which was true and is no longer enough, because an activation taken ninety-one days ago has expired from the stream, and a runtime restarted after that finds no decision and pauses the persona, silently, with no restart of the Gateway involved. This ADR records that consequence rather than hiding it inside the number: the runtime already holds the service token that opens the consent snapshot (since [#184](https://github.com/linagora/twalk/issues/184)), the snapshot already carries every persona decision, and reading it at startup is the remedy — a follow-up and not part of this decision, so that the retention policy is not held hostage to it. **[ADR 0012](0012-revoked-consent-reduces-publication.md) said "events already on the bus stay until retention expires"** when retention was for ever, which meant a revoked contact's full-bodied messages stayed on the bus indefinitely; this ADR is the first time "until retention expires" names a date, and ninety days is still ninety days of a revoked contact's words — revocation applies to the future only, and an operator who wants them gone sooner has a purge, which is theirs and not Twalk's. **ADR 0028 is not built yet**, so the contact's words it moves onto a seven-day stream are today on `twalk` under the ninety days set here, and this ADR does not pretend otherwise: the identity half was always going to be ninety, and the words half is ninety until that ADR lands. **The day of duplicate tracking bounds the ordinary restart and not a rebuild**: a Sensor started with an empty state directory performs an initial sync and can republish events older than a day, which land twice — the deterministic ids downstream (a persona's suggestion id, which is also its `Nats-Msg-Id`) are the second line and the only one — and the window cannot be longer than the age, so a deployment that shortens one shortens the other. **Applying the age to an existing stream expires, immediately, every event older than it**: the reconciliation says so in its last line, and on the reference deployment there is nothing that old, but a stream that has run unbounded for a year loses nine months of it at the next Sensor restart, which is why the policy is in `.env.example` beside the other knobs and not only in this document. And a field JetStream cannot change in place — the reference deployment's stream is file storage with one replica, so none applies to it, but a stream somebody created in memory does — leaves the Sensor running on a policy it did not choose, saying so at `error` on every start until the operator either accepts it or takes the stream down themselves; that is a cost of never recreating a stream, and it is the right one, because the alternative is a restart that deletes other people's messages.
