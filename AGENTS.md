# AGENTS.md

## Project overview

`twalk` is the monorepo for Twalk, a sovereign, open-source, self-hosted event hub for personal multi-channel messaging (WhatsApp, Signal, SMS, Telegram, Discord). Messaging traffic lands in Matrix portal rooms via Mautrix bridges, is normalised by the Sensor into versioned CloudEvents on a NATS JetStream bus, and is consumed by Hermes-hosted personas under human oversight. See `README.md` for the full picture and `CONTEXT.md` for the domain vocabulary.

As of 2026-09-17 the repository contains documentation, the complete event contract, and the shared integration-test harness — no component implementation yet:

- `README.md`, `docs/wireframes/companion-v0.1.md`, `docs/architecture/roadmap.md` (milestones ↔ lots), `docs/architecture/adr/` (ADRs 0005–0009 written; numbers 0001–0004 are referenced from the docs but not yet written)
- `contracts/cloudevents/v1/` — the complete v1 contract: 10 CloudEvents schemas plus one validated fixture per type, and `fixtures/variants/<type>/<variant>.json` for a shape the schema only allows under a condition (a revoked sender's reduced message, ADR 0012)
- `.scratch/sensor/` — local mirrors of the Sensor spec and tickets 01–11; **canonical is the tracker: GitHub Issues on [linagora/twalk](https://github.com/linagora/twalk/issues)** (conventions in `docs/agents/issue-tracker.md`); all 11 tickets are done and merged
- `sensor/` — the Sensor Cargo package: library modules (`config`, `consent`, `metrics`, `network`, `normalize`, `outbound`, `owner` — pure logic) plus the binary wiring to matrix-sdk and NATS in `src/main.rs`; integration tests in `sensor/tests/` (`smoke.rs`, `sensor_lifecycle.rs`, `message_to_event.rs`, `consent.rs`, `reactions.rs`, `presence.rs`, `outbound.rs`, `outbound_message_sent.rs`, `owner_is_never_a_contact.rs`, `persistence.rs`, `fidelity.rs`, `encryption.rs`, `observability.rs`, `deployment.rs`, `bridges_deployment.rs`) over the Sensor-specific half of the harness in `sensor/tests/harness/` (the Matrix `Bot`, the portal helpers, `SensorProc`, `crypto.rs` for Megolm-capable bots, `gateway.rs` for the stub Companion Gateway). Since ticket #51 `consent` also holds the Sensor's one HTTP seam: it reads the Gateway's consent snapshot with a service token (`SENSOR_GATEWAY_URL`, `SENSOR_GATEWAY_SERVICE_TOKEN`), applies it and creates the `consent.state.changed` consumer at the sequence it names (ADR 0010), which is what keeps a granted contact granted across a restart. Since ticket #109 the Sensor also knows **who its operator is** (`owner`): a message from one of the identities the deployment confirmed as the user's own (`SENSOR_OWNER`, `SENSOR_OWNER_IDENTITIES`) is published as `outbound.message.sent`, with the operator's Matrix ID as the subject and no `consent` extension at all — the user is not a contact and never enters the consent model (ADR 0018). The set is handed over, never derived: the operator has several network ghosts per network (`@whatsapp_<phone>` *and* `@whatsapp_lid-<lid>`), and a bridge's `whoami` reports a login id and no ghost Matrix ID at all. An unconfirmed identity stays a contact. Ticket #147 extended that to the rest of the traffic (ADR 0021): the operator's own reaction is `outbound.reaction.added`, on the same terms, their own **presence is not published at all** — it told nobody anything and was the bulk of the stream — and the consent cache refuses entry to any decision about one of their identities, from the snapshot or the stream alike, because the owner has no consent state. Ticket #105 added the one thing the Sensor could not previously say about itself: `twalk_sensor_observed_rooms`, how many rooms it is actually reading — observation scope is invitation-driven and starts empty, which is the right default and also the shape of the worst defect this product has had — and `twalk_sensor_invites_total{outcome}`, where `ignored` counts an invitation from a user `SENSOR_ALLOWED_INVITERS` does not name. That refusal is correct and was silent, and on a deployment whose bridge bots were left out of that list it is the only trace of why a conversation the user chose never reached the bus (`tests/observability.rs`). `sensor/tests/owner_is_never_a_contact.rs` reads the contract directory and fails on any type whose `subject` is a Matrix user ID and which has no recorded answer to "what happens when that person is the owner?", so an eleventh type cannot be added without the question being asked
- `tests/harness/` — the `twalk-test-harness` Cargo package, shared by every component's suite: the test stack's lifecycle (`compose.test.yaml`, Synapse config, bot provisioning), the `Bus`, contract validation, `poll_until`, and a stub OpenAI-compatible LLM for persona tests. A dev dependency of `sensor/` and `hermes/`
- `hermes/` — the `twalk-hermes` Cargo package, in two halves. The **runtime** (ticket #23) is `src/`: it reads its persona list from the environment (`HERMES_PERSONAS`, a JSON array of an id and an argv), starts one process per persona, restarts a crashed one with exponential backoff, follows `consent.state.changed` from the beginning of the stream to learn which personas the user activated, and stops cleanly on SIGTERM — every transition a structured log, and no telemetry of its own, because observability is OTLP and opt-in (ADR 0017). Three of its decisions are load-bearing and each lives in its own module. `environment` **constructs** a persona's environment rather than letting it inherit the runtime's: the Companion Gateway's service token also opens the consent snapshot — the list of every contact — and a persona has no business holding that to learn which model to call (ADR 0015), and a third-party persona takes the same path as a first-party one (ADR 0008), so the control is that the variable is not there. `activation` moves a **consumer**, never a process: a paused persona still runs and receives nothing (ADR 0013), which the runtime renders as the filter subject of the durable consumer it owns — the inbound subject when active, `<prefix>.hermes.paused.<persona id>` (which nothing ever publishes on) when paused; `supervisor` cannot see the activation state at all, which is how that stays true. Per-network scoping is *not* enforced at the bus, because a subject carries no network. `supervisor` separates a crash from a persona that never started: a run shorter than `HERMES_PERSONA_HEALTHY_AFTER_MS` does not count, and `HERMES_PERSONA_START_FAILURES` of those in a row is announced once as `persona failed to start`, so a runtime that cannot start something is never indistinguishable from one that is still starting it. A persona that cannot reason fails three ways and each has its own message: no model configured is the runtime's refusal to start, and unreachable-endpoint versus refused-request are the SDK's client in the persona's log. The one case only the runtime can see is an endpoint on **this host's loopback** — a perfectly good address (the reference deployment publishes a LiteLLM proxy there) that a persona in a container of its own network namespace dials as itself — so it warns at startup and names the fixes; making that address reachable is the deployment's job, not the runtime's, and `deploy/docker-compose/` answers it since ticket #158 by putting the runtime and its personas in the host's network namespace (ADR 0023). `hermes/README.md` holds every environment variable, including `HERMES_LLM_API_KEY_FILE`, which **wins** over `HERMES_LLM_API_KEY` so a production stack can lock the credential down (ADR 0015) — on a real deployment the model name comes from the browser and the key from a file, so that is the ordinary combination rather than the exotic one. The **persona** half is `personas/assistant/`, the reference persona (ticket #21): a container image built on the Python SDK that consumes `inbound.message.received` and publishes `persona.thinking.emitted` then `persona.suggest.produced`, with the consent gate, the deterministic ids and the headers all coming from the SDK. Integration tests in `hermes/tests/`: `smoke.rs` exercises the shared harness against the real stack, `suggestion.rs` is the suggestion policy (ticket #22) — every suggestion carries an `expires_at` one operator-set window (`TWALK_SUGGESTION_TTL_SECONDS`, an hour by default) after it was *produced*, not after its trigger, and a trigger the bus redelivers stays one suggestion at attempt 1 — and `assistant.rs` is the spec's seam 1 — the real persona **container**, driven by publishing contract fixtures to the bus with the stub LLM behind it, asserting the two events' schema validity, ids, headers and continued trace, and asserting the consent gate by the absence of both events and of any LLM call. `runtime_lifecycle.rs` is seam 2 — the real `twalk-hermes` binary starting the real persona image, asserting the three acceptance criteria and three absences (a paused persona receives nothing while still running; a persona's container environment holds none of the runtime's credentials; a persona whose image will not run is announced as failed). The Hermes-specific half of the harness is `hermes/tests/harness/`: `PersonaRun`, which runs the persona image under its own compose project on a bus namespace of its own run (the persona container uses host networking, so it reaches the stack's published NATS port and the in-process stub LLM on loopback), and `RuntimeRun`, which runs the runtime and lets *it* start the persona — through `tests/run-persona-image.sh`, the argv the runtime is configured with in tests, which runs the image with whatever environment the runtime gave it and forwards every variable, so that an assertion about what a persona does not hold is worth making
- `sdk/python/` — `twalk_sdk`, the Python persona SDK (ticket #21), and the reason a persona author cannot breach consent by forgetting: **the consent gate lives in the SDK** (`consent.py`, applied before the author's handler and before the LLM client is touched, deciding on the envelope's `consent` extension alone so it never depends on a body a reduced event does not have — ADR 0012), alongside the contract's `persona.*` envelopes and their deterministic ids (`envelope.py`, whose output reproduces the contract's own fixtures), the durable pull consumer, the publishing with `Nats-Msg-Id` and the duplicated `network`/`consent`/`traceparent` headers, the suggestion policy (`policy.py`, ticket #22: the expiry every suggestion carries, and the attempt that counts suggestions rather than deliveries), the process loop (`persona.py`) and an OpenAI-compatible chat-completions client (`llm.py`). No default LLM (ADR 0015): a persona refuses to start without the endpoint *and* the model the operator named, and `TWALK_LLM_PARAMS` is a JSON object of provider parameters merged into every request untouched — a parameter set to `null` removes a field the request would otherwise carry, which is how a provider that rejects one is made to work; in a deployment that configuration comes from the Gateway and is injected by the runtime (#23). Packaged as a container image, never installed on a host (no pip — PEP 668 — and no venv module). Its pure half is stdlib-only and unit-tested in place against the contract's fixtures (`sdk/python/tests/`, `python3 -m unittest discover -s tests`); `Persona` and `Llm` are imported lazily, which is what keeps that possible. `sdk/python/README.md` holds the decisions and every environment variable

`approval` and `approval_http`, `POST /api/approvals`, the human act that turns one suggestion into an outbound reply — it reads the suggestion and the message it answers off the bus (a bounded search whose bound is visible in the answer: `410 suggestion_out_of_reach` is never `404 suggestion_not_found`), refuses an expired suggestion, refuses one whose trigger was never consented, and refuses one whose sender's consent is no longer `granted` **at that moment**, which is a read of this Gateway's own journal and not a question asked of another process — spec #19 had put this endpoint on the Hermes runtime and ADR 0022 records why it moved, so the Gateway now produces a third event type, `persona.reply.approved.v1`, whose `source` still names the persona whose suggestion it was. There is no outbox on that path, deliberately: a consent decision is committed then published because it must not be lost, and an approval is published inside its own request or refused because a send held for later is a send whose consent check has gone stale — and the row it writes afterwards holds no message content, only the suggestion's id, who approved it, whether they edited it and where the publication landed, which `GET /api/approvals/{id}` reads back so that "did my reply go out?" is never a spinner — and **reading** those suggestions (ticket #97): `suggestions` and `suggestions_http`, `GET /api/suggestions` and `GET /api/suggestions/{id}`, the listing #100's approval screen draws from, which #24 had left the Companion with no way to build because nothing on this origin could *find* a suggestion. It is a **projection of the bus and not a second store** — the suggestion lives in the stream, the Gateway keeps no copy, so a replay and the list cannot disagree with nobody able to say which is true; the cost is that the read is bounded by the same window the approval lookup uses and the bound is **in the answer** (`window.reached_start_of_stream`), never only in the configuration. What it says about the message a suggestion answers is that message's id and its type and nothing else: an excerpt belongs to the author of the quoted message rather than to whoever sent the event carrying it (#110, ADR 0012), so this module never opens an inbound event at all — which is what `tests/suggestions.rs` asserts by publishing a trigger whose body, third-party excerpt, display name and `network_identifier` are distinctive markers and searching every byte of every answer for them, for a granted contact and for one revoked after the fact. An expired suggestion, a missing one and an already-approved one are three answers (`standing: expired`, `404 suggestion_not_found`, `standing: approved` with #24's record), and a suggestion the read did not reach is `410 suggestion_out_of_reach` — the same codes and statuses `POST /api/approvals` gives for the same facts, because two doors onto one fact must not teach a client two vocabularies — and its own HTTP description (ticket #63): `companion-gateway/openapi.yaml`, an OpenAPI 3.1 description of the whole origin, served at `/openapi.yaml` by `openapi` (which embeds it) and **extended by every ticket that adds an endpoint**, because `tests/openapi.rs` fails on a route it does not describe — and the pending-contact projection (ticket #54): `contacts` and `contacts_http`, a **durable consumer** on `inbound.message.received` that makes the Gateway a consumer of the bus as well as its producer, keeping **only** a contact's Matrix ID, the network it wrote on and its first and last sighting, so the Companion can say how many decisions are waiting; no body, no display name and no `network_identifier` reach that store, which is enforced by the shape of the types (the event is deserialised into a struct with no `data` member) and asserted against the store's own bytes. — and the **model and language configuration** (ticket #98): `settings` and `settings_http`, the endpoint, the model name, the provider passthrough, the endpoint credential and the user's native language, held here because an operator must be able to change a model without shell access and because the Hermes runtime injects the result into each persona rather than letting a persona fetch it — the service token that reads this configuration is the token that opens the consent snapshot (ADR 0015, ADR 0016), which is why `GET /api/settings/runtime` is the second and last row of #52's service-token table. Three decisions in it are the ones to argue with. The credential is **write-only**: `PUT` takes it, no browser-facing read returns it (only whether one is configured, which source is in force and its last four characters), and the one answer that carries it is the runtime's — and a credential the operator supplied as a file (`GATEWAY_LLM_API_KEY_FILE`, the same host path compose gives the runtime) **wins** over one set from the browser, which is not a theoretical precedence but how the reference deployment runs: the model name from the Companion, the key from a file. The provider passthrough stays, because an operator without a proxy needs it, and is documented as the **escape hatch** rather than the norm — with an OpenAI-compatible proxy in front (LiteLLM before Qwen at OVH, the reference shape) Twalk sees a plain endpoint serving a model called `qwen` and every provider quirk stays in the proxy. And `POST /api/settings/model/probe` sends one one-token completion so that an endpoint that cannot be reached, one whose request was refused, one answering something that is not a completion and **no endpoint configured at all** are four different answers rather than one silence — the same trichotomy holding one level up, where a runtime told `llm: null` knows the operator named no model and does not confuse that with a Gateway it could not reach. It ships #164's Gateway half: ADR 0016's language fallback finally has a value to fall back to. The credential lands in `settings.sqlite3`, which nothing encrypts at rest (#14), so it is in `docs/architecture/security-model.md`'s credential table and its residual risk 15. — and the **portal register** (ticket #105, ADR 0024): `portals` and `portals_http`, `GET /api/portals` and `POST /api/portals/observation`, which answer the defect that made a freshly connected network publish nothing at all. A bridge builds a portal room *lazily*, as each conversation becomes active — eighteen appeared on the reference deployment between 04:54 and 13:24 — and invites only the user, so nothing ever put the Sensor inside one and the deafness grew on its own; a fix aimed at the rooms that exist when a network is connected would have been right for an hour. The register reads each bridge's portal rooms **as that bridge's own bot**, through the appservice token ticket #56 already put in configuration, which makes this the first thing on the origin that *acts* with that token rather than only verifying a push with it (`docs/architecture/security-model.md`). It is **a projection of the homeserver and not a store**: whether a conversation is observed is the Sensor's own `m.room.member` event, asked again on every read, so a reconnection that rebuilds every portal is simply the next answer. What it refuses to do is the load-bearing part — the mechanism is the Gateway's and the policy is the user's, one conversation at a time (#143), so **nothing is observed by default**: those eighteen rooms held some 1,300 memberships and observing them all is the decision #122 is about. And it states a number the product previously could not say at all — `summary` in the answer, `twalk_companion_gateway_portal_rooms{observation}` on `/metrics` — with every configured bridge listed readable or not, so "the Sensor is outside 17 of your 18 conversations" never quietly means "…of the 18 I could see". A portal stuck at `invited` is its own diagnosis: the Sensor refused the inviter, which is `SENSOR_ALLOWED_INVITERS` missing that bridge's bot — Integration tests in `companion-gateway/tests/` (`service.rs`, `signin.rs`, `consent.rs`, `consent_snapshot.rs`, `bootstrap.rs`, `pending.rs`, `approvals.rs`, `settings.rs`, `bridges.rs`, `bridge_status.rs` — the last two against a stub bridge implementing the provisioning contract, `tests/harness/stub_bridge.rs`, because a real mautrix bridge needs a live account and a phone — `portals.rs`, against real portal rooms on the real homeserver, whose keystone assertion is a portal created *after* the Gateway was already running — and `openapi.rs` at the process boundary, `deployment.rs` against the compose stack — where the Sensor runs beside the Gateway, joins the room it is invited to and publishes that room's traffic as `network=matrix`)

The runtime and its persona containers share the **host's network namespace**, which is what lets a persona reach an LLM proxy on `127.0.0.1` (the reference shape) and the bus on its published port with the one URL the runtime injects. The persona's image is built by a one-shot service that exists to be built (`persona-assistant-image`), the persona's argv is `run-persona <container> <image>` (`run-persona-image.sh`, shipped in the Hermes image), and a Hermes given no persona list or no model starts, hosts nothing and says which variable is missing — `hermes-entrypoint.sh` — so a stack without an LLM still comes up

Four decisions make it what it is. It **cannot name the contact** and says so on the screen: `GET /api/suggestions` carries the trigger as an id and a type and nothing else (#97), because naming the sender means opening their message — the leak #110 closed (ADR 0012) — so `rows.ts` has no member a contact could go in, there is no second read anywhere, and `approvals.whoIsIt.*` tells the user it is a decision rather than a defect; the open question is #160's and building the screen is the evidence it was waiting for (one suggestion reads fine alone; *two at once* are indistinguishable, which is the real cost). Every refusal has a **sentence and a next step**: `refusal.ts` is the table for the Gateway's fifteen codes plus the three malformed-request ones, `Explained` has no value meaning "still working" so a refusal cannot render as a spinner (#111, #135, #139), `approval_published_but_not_recorded` carries `sent: true` because that reply *did* go out, and `refusal.test.ts` parses `companion-gateway/openapi.yaml` in both directions so the table cannot fall behind the Gateway or outlive it. **Refusing is local and says so**: no route on this origin refuses a suggestion and none could without a second store or a new contract event, so `dismissed.ts` hides the row in this browser, the copy states all four consequences, and the journey asserts the Gateway still calls the suggestion `approvable` afterwards. And the **dashboard gets a count and a link**: `summary.ts` reduces the listing to two numbers at the seam, the same way `pending.contacts` is dropped, so no component could render a persona's words by accident. A **lost reply** — `standing: approved` with `publication: unpublished` — is listed with its text and a *Send it again* that republishes under the same deterministic id; the other kind, a reply the Sensor could not post after the bus acked it, is not visible from this origin at all and no row is invented for it. `tests/e2e/approvals/` is its own Playwright project on the bridge Gateway's origin, after `dashboard`, publishing the suggestion onto the bus itself and reading `persona.reply.approved.v1` back off NATS. — and the **consent screen** (ticket #170): `/consent` and `src/lib/consent/`, the interface the product's central promise had none of, which until now meant the owner's first consent decision on the reference deployment was made with a hand-forged HTTP request. `model.ts` carries **two** facts per row rather than one — `state` (`granted`, `pending`, `revoked`) and `decidedBy` (`contact`, `network`, `nothing`) — because ADR 0010 is explicit that an absent subject means no decision was ever recorded and never a revoked one, and never-decided is the default of the whole model and most of a real list; `awaiting` is `decidedBy === 'nothing'` and deliberately not a synonym for `state === 'pending'`, which is the same line `GET /api/contacts/pending` draws. `withholds` is a function rather than an adjective in a catalogue, because only `revoked` reduces what is published (ADR 0012) and copy implying that undecided means unseen would be a comforting untrue thing; and the screen says twice that none of it is retroactive, since the label is stamped at publication and a user who grants a contact and sees nothing happen would otherwise conclude the product is broken. `bulkDecisions(shown, state)` is #137's rule with higher stakes — it takes the rows the filter shows, the number on the button *is* that array's length, no function in the module takes the whole list, and it asks twice — while answering for a whole network is not offered at all, because it decides for people who have not written yet (#122). The owner is **labelled, not filtered** (ADR 0018, ADR 0021): a row about them is #149's Gateway half showing through, hiding it would hide the only symptom a user can see, and what a browser can recognise is the canonical Matrix ID and not the network ghosts that ticket is about. `tests/e2e/consent/` is the only Companion suite that starts a **real Sensor** (`tests/e2e/consent/sensor.ts`), with **no Gateway snapshot configured** so its cache starts cold and everything is `pending` — a `granted` label on a subsequent message can then only have come from the decision the browser took, through the Gateway's outbox, onto the bus, into the Sensor's cache — and it is the one shape of that journey no other suite covers, since `sensor/tests/consent.rs` proves relabelling on WhatsApp from a decision the test itself published. The onboarding journey is walkable end to end from here: account, recovery key, a network, the assistant, the dashboard, asserted as one journey in `tests/e2e/bootstrap.spec.ts`. Playwright is authoritative (`tests/e2e/`), over the built export served by `tests/serve-like-gateway.mjs` — which transcribes the Gateway's own path resolution, and which under `npm run test:e2e:stack` puts a real Gateway and a real Synapse behind `/api`: `tests/real-stack.mjs` starts one Gateway for the bootstrap journey (an owner whose account does not exist yet) and a second for the bridge journeys (an owner whose account does, with `tests/stub-bridge.mjs` configured as its bridges, and a bus, because #69's journey reads the consent event it caused straight off NATS — `tests/e2e/dashboard/bus.ts`), and a third for the session journeys (`tests/e2e/session/`, ticket #111), identical to the second except that its `GATEWAY_DEVICE_TOKEN_TTL` is five seconds, so a browser can be watched losing a session and getting it back — the ticket asks for the expiry to be arranged at the Gateway rather than waited for, and that lifetime is deployment-wide, so it cannot live on the origin every other spec uses. `companion/README.md` holds the decisions
- Other component directories hold stub READMEs only: `ui/`, `examples/`, `tools/`

## Build and test commands

Requires Docker (the harness brings up its own Synapse + NATS stack) and a Rust toolchain.

Four Cargo packages, each with its own lockfile and target directory — there is no workspace, so build and test each from its own directory:

```bash
cd sensor
cargo build --tests   # compile / typecheck
cargo test            # full suite: boots the stack itself, ~15s cold, ~3s warm

cd ../hermes
cargo test            # Hermes suite: shares the same test stack, and builds the persona image itself

cd ../companion-gateway
cargo test            # Gateway suite: the binary at its process boundary, plus its compose service

cd ../tests/harness
cargo test            # the shared harness's own unit tests (no Docker)
```

The Python SDK's pure half — the consent gate, the envelopes, the configuration — is stdlib-only, so its unit tests need neither pip nor Docker (there is no pip on the host, by design: personas ship as images):

```bash
cd sdk/python
python3 -m unittest discover -s tests   # the gate, the deterministic ids, the envelopes
```

The Companion is the one non-Cargo component: Node 22 and npm, from `companion/`.

```bash
cd companion
npm ci                # install; runs `svelte-kit sync`
npm test              # api:check + svelte-check + Vitest + build + Playwright
npm run test:e2e:stack  # the same Playwright suite with a real Gateway and Synapse behind /api
npx playwright install chromium   # once, before the first `npm run test:e2e`
```

`npm test` needs neither Docker nor Rust: the bootstrap journey
(`tests/e2e/bootstrap.spec.ts`) skips itself with a reason. `npm run
test:e2e:stack` is the one that runs it, bringing up the shared test stack and
building the Gateway binary (`TWALK_TEST_STACK`, `TWALK_TEST_SYNAPSE_PORT`,
`TWALK_TEST_NATS_PORT` move the stack aside; `TWALK_TEST_PORT` moves the
Companion's own origin, which matters when another worktree is running its
suite).

`npm run api:check` is the one to remember when working on the Gateway: it fails when `companion/src/lib/api/` no longer matches `companion-gateway/openapi.yaml`, and `npm run api:generate` in `companion/` is the fix.

The Sensor and Hermes suites bring up the same test stack (one Synapse, one NATS JetStream), each on its own bus subjects; `TWALK_TEST_STACK`, `TWALK_TEST_SYNAPSE_PORT` and `TWALK_TEST_NATS_PORT` move a stack aside for a parallel worktree. The Hermes persona tests take that further, because a durable consumer over the shared `twalk.>` history would replay every message another suite ever published: each gives the persona a JetStream stream and a bus subject prefix of its own run (`TWALK_BUS_SUBJECT_PREFIX`, `twalk` in every deployment), and deletes the stream and the container when it is done. The Companion Gateway's suite uses the same stack: real Synapse mints the OpenID tokens its sign-in tests need and answers the admin registration call bootstrap relays (the test Synapse serves the `openid` resource for the first), and its consent tests publish to the same NATS JetStream, reading back the events they caused by the ids the write API returned. Its process-boundary tests ask the kernel for a free port, and its pending-contact suite publishes contract-valid inbound events onto the same JetStream and reads the list back over HTTP; its deployment test uses the deploy-stack variables (`TWALK_DEPLOY_TEST_STACK`, `TWALK_DEPLOY_TEST_GATEWAY_PORT`, `TWALK_DEPLOY_TEST_SYNAPSE_PORT`, `TWALK_DEPLOY_TEST_NATS_PORT`) the Sensor's deployment test established — its bootstrap test is the one that needs the bus, since it asserts the invited room's traffic on it. `sensor/tests/bridges_deployment.rs` runs the reference deployment a third time, with the `bridges` profile on, under its own `TWALK_BRIDGES_TEST_*` project, ports and teardown flag — its module docs list them. `companion-gateway/tests/portals_deployment.rs` runs it again on a stack of its own (`TWALK_PORTALS_TEST_STACK`, ports 17309/17319/17329, `TWALK_PORTALS_TEST_KEEP=1` to keep it): the whole deployment comes up first, a portal room is built afterwards, the user chooses it, the **real Sensor** joins on the bridge bot's invitation and the conversation reaches the bus — and it tears its stack and its per-stack images down at the end of every run, passing or failing. `hermes/tests/full_loop.rs` runs it a fourth time, because the full loop needs a real Sensor to post the approved reply, a real Gateway to serve the approval and — since #158 — the deployment's own Hermes to produce the suggestion: its own `TWALK_LOOP_TEST_STACK` project and ports 19508/19518/19522 (`TWALK_LOOP_TEST_SYNAPSE_PORT`, `TWALK_LOOP_TEST_GATEWAY_PORT`, `TWALK_LOOP_TEST_NATS_PORT`), and — unlike the other three — it tears its stack and its per-stack images down at the end of every run, passing or failing (`TWALK_LOOP_TEST_KEEP=1` keeps them).

## Code organization

Monorepo with 13 top-level directories — see the "Repository layout" section of `README.md`. Stacks: Rust for `sensor/`, `hermes/` and `companion-gateway/`, SvelteKit (static export) for `companion/`, Python for `sdk/python/` and the personas in `hermes/personas/` (ADR 0008: the runtime is Rust, personas are separate processes and Python's LLM ergonomics stay inside them). The Sensor test harness speaks the Matrix client-server API over plain HTTP — the HTTP `Bot` helpers deliberately do not depend on matrix-sdk; the exception is the `CryptoBot` helper (`sensor/tests/harness/crypto.rs`), which runs matrix-sdk with its crypto stack because raw HTTP cannot Megolm-encrypt.

## Code style guidelines

**Do not run a formatter.** There is no Prettier, rustfmt-on-save or equivalent configured anywhere in this repository, and none is wanted: the style is tabs, single quotes and a ~100-column wrap in the TypeScript and Svelte, and `cargo fmt` defaults in the Rust, all maintained by attention. A `npx prettier --write` here resolves to whatever binary is on the machine, applies *its* defaults, and rewrites whole files — two merges once turned a 200-line change into 1560 insertions and 1464 deletions, which had to be undone by hand. Match the file you are editing. (`cargo fmt` is the one exception, and only because the Rust crates were written to it.)

In all naming and prose, follow the `CONTEXT.md` vocabulary: **network** (never "channel" outside user-facing copy, never a bridge name like `gmessages`), **persona** (never "bot" for agent identities — test Matrix users standing in for bridges are "test bots"), **the Companion** means the PWA only, **Companion Gateway** always in full.

## Testing instructions

Tests live at the agreed seam: the component's process boundary (real Synapse + real NATS JetStream). What every suite shares is in the `tests/harness/` crate (stack lifecycle, `Bus`, `validate_against_contract`, `poll_until`, the stub LLM); component-specific helpers stay with their component (`sensor/tests/harness/` and `hermes/tests/harness/` both re-export the crate, so each component's test files see one flat `harness::` namespace). For a persona the process boundary is a **container's**: `hermes/tests/harness/`'s `PersonaRun` brings up the image the persona ships as, and a test asserts only what appeared on the bus and what the stub LLM was sent. New test files go beside `smoke.rs`. Every event-producing behaviour must assert schema validity via `validate_against_contract`. Keep tests isolated from persisted stack state (unique rooms and bus subjects per run).

## Security considerations

Never commit secrets, credentials, or `.env` files (`.gitignore` covers `.env`). The only secrets in the repo are the throwaway constants in `tests/harness/synapse/homeserver.yaml` and the test-bot passwords — local, ephemeral test stack only; never reuse them elsewhere. Message content is highly sensitive by design: no message may leave the user's infrastructure without explicit consent — keep that invariant in mind for any code that touches event payloads.
