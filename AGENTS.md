# AGENTS.md

## Project overview

`twalk` is the monorepo for Twalk, a sovereign, open-source, self-hosted event hub for personal multi-channel messaging (WhatsApp, Signal, SMS, Telegram, Discord). Messaging traffic lands in Matrix portal rooms via Mautrix bridges, is normalised by the Sensor into versioned CloudEvents on a NATS JetStream bus, and is consumed by Hermes-hosted personas under human oversight. See `README.md` for the full picture and `CONTEXT.md` for the domain vocabulary.

As of 2026-09-17 the repository contains documentation, the complete event contract, and the shared integration-test harness — no component implementation yet:

- `README.md`, `docs/wireframes/companion-v0.1.md`, `docs/architecture/roadmap.md` (milestones ↔ lots), `docs/architecture/adr/` (ADRs 0005–0009 written; numbers 0001–0004 are referenced from the docs but not yet written)
- `contracts/cloudevents/v1/` — the complete v1 contract: 10 CloudEvents schemas plus one validated fixture per type, and `fixtures/variants/<type>/<variant>.json` for a shape the schema only allows under a condition (a revoked sender's reduced message, ADR 0012)
- `.scratch/sensor/` — local mirrors of the Sensor spec and tickets 01–11; **canonical is the tracker: GitHub Issues on [linagora/twalk](https://github.com/linagora/twalk/issues)** (conventions in `docs/agents/issue-tracker.md`); all 11 tickets are done and merged
- `sensor/` — the Sensor Cargo package: library modules (`config`, `connection`, `consent` — the I/O half since #273; the decisions are `consent-cache/`'s —, `metrics`, `network`, `normalize`, `outbound`, `owner_device` — pure logic) plus the binary wiring to matrix-sdk and NATS in `src/main.rs`; integration tests in `sensor/tests/` (`smoke.rs`, `sensor_lifecycle.rs`, `message_to_event.rs`, `consent.rs`, `reactions.rs`, `presence.rs`, `presence_network.rs`, `bridge_bots_are_not_contacts.rs`, `outbound.rs`, `outbound_message_sent.rs`, `owner_is_never_a_contact.rs`, `persistence.rs`, `fidelity.rs`, `encryption.rs`, `observability.rs`, `deployment.rs`, `bridges_deployment.rs`) over the Sensor-specific half of the harness in `sensor/tests/harness/` (the Matrix `Bot`, the portal helpers, `SensorProc`, `crypto.rs` for Megolm-capable bots, `gateway.rs` for the stub Companion Gateway). Since ticket #51 `consent` also holds the Sensor's one HTTP seam: it reads the Gateway's consent snapshot with a service token (`SENSOR_GATEWAY_URL`, `SENSOR_GATEWAY_SERVICE_TOKEN`), applies it and creates the `consent.state.changed` consumer at the sequence it names (ADR 0010), which is what keeps a granted contact granted across a restart. Since ticket #109 the Sensor also knows **who its operator is** (`owner`): a message from one of the identities the deployment confirmed as the user's own (`SENSOR_OWNER`, `SENSOR_OWNER_IDENTITIES`) is published as `outbound.message.sent`, with the operator's Matrix ID as the subject and no `consent` extension at all — the user is not a contact and never enters the consent model (ADR 0018). The set is handed over, never derived: the operator has several network ghosts per network (`@whatsapp_<phone>` *and* `@whatsapp_lid-<lid>`), and a bridge's `whoami` reports a login id and no ghost Matrix ID at all. An unconfirmed identity stays a contact. Ticket #147 extended that to the rest of the traffic (ADR 0021): the operator's own reaction is `outbound.reaction.added`, on the same terms, their own **presence is not published at all** — it told nobody anything and was the bulk of the stream — and the consent cache refuses entry to any decision about one of their identities, from the snapshot or the stream alike, because the owner has no consent state. Ticket #105 added the one thing the Sensor could not previously say about itself: `twalk_sensor_observed_rooms`, how many rooms it is actually reading — observation scope is invitation-driven and starts empty, which is the right default and also the shape of the worst defect this product has had — and `twalk_sensor_invites_total{outcome}`, where `ignored` counts an invitation from a user `SENSOR_ALLOWED_INVITERS` does not name. That refusal is correct and was silent, and on a deployment whose bridge bots were left out of that list it is the only trace of why a conversation the user chose never reached the bus (`tests/observability.rs`). Tickets #152 and #150 finished the question ADR 0021 left open, "which of the accounts the Sensor observes are people?" (ADR 0026, ADR 0027). A **bridge bot** — mautrix's `sender_localpart`, `@whatsappbot`, `@signalbot` — is the appservice's own service identity and not a person, so nothing is published about it on any type and no consent decision about it enters the cache: the set is `SENSOR_BRIDGE_BOTS`, handed over like the owner's identities and for the same reason, since every available inference (reusing `SENSOR_ALLOWED_INVITERS`, which also names the operator; reading the portal's own `m.bridge` marker, which is attacker-influenced room state) can suppress a real person instead — and here the safe failure runs the *other* way from the rest of this project, because mistaking a contact for a bot deletes them from the bus in silence, so unknown is not a bot and `tests/bridge_bots_are_not_contacts.rs` proves the bot dropped and a contact in the same room still published, separately. It was not a tidiness complaint: two bots were 1,150 of the reference deployment's 1,216 presence events, two a minute forever, each one routed through the *contact* machinery, so the consent state could acquire a row about a robot. And an `inbound.presence.updated` event's **network is now the subject's**, not the first shared room's in id order (`network::subject_network`): presence is not room-scoped, so a ghost is attributed by its own localpart, an account that shares a room no bridge marked is `matrix` (a bridge never puts its ghosts in one, so that membership is evidence rather than a guess — the reverse of `network::resolve`'s precedence, which stays right for a *room's* traffic), and a subject in portals of two networks that is a ghost of neither is **not published at all** rather than published under a sort. That mattered because consent is keyed on `(subject, network)`: `tests/presence_network.rs` asserts the consequence rather than the label, staging a native Matrix contact the user revoked on `matrix` inside a WhatsApp portal on a deployment that granted WhatsApp as a whole, where the old behaviour answered `granted`. Both suppressions are counted (`twalk_sensor_events_dropped_total{reason}`), because a silence is the one failure this product has shipped repeatedly without noticing. Ticket #123 gave the Sensor the one thing the outbound half had never had, an **identity** (`owner_device`, ADR 0025, ADR 0034): a **second, write-only Matrix client**, a device of the owner's own account (`SENSOR_OWNER_DEVICE_ACCESS_TOKEN`, `SENSOR_OWNER_DEVICE_ID`), beside its own `@sensor:` client — because a mautrix bridge relays to its network only what the **logged-in user's own Matrix account** sends, so an approved reply from `@sensor:` was ignored without a log line while Synapse returned an event id and every component reported itself healthy. One identity observes and one acts, and the observing one keeps every property ADR 0024 and the consent gate rest on: the second client registers no event handler, publishes nothing, and is never what `joined_rooms()` answers for the register. Five decisions in it are the ones to argue with. It **joins a room only when a bridge bot `SENSOR_BRIDGE_BOTS` names invited it** — the inviter is the one authenticated fact in an invitation, while the room id, the room's name and its `m.bridge` marker are all chosen by whoever sent it, and this device *posts messages*; `SENSOR_ALLOWED_INVITERS` is deliberately not reused, since it also names the operator, whose own invitations would then be a way to place their device in any room at all. Its sync is **the minimum Megolm needs and nothing more**: matrix-sdk's send path syncs the members, queries the keys and shares the room key by itself, so what the loop is for is the Olm machine's own device-key upload (dispatched by `sync_once`) and seeing invitations — with a filter asking for zero timeline events, which is ADR 0034's "it never reads history" as a request parameter rather than a promise, and `set_presence: offline`, because syncing as online would have Synapse broadcast the owner's account as present to everyone sharing a room with them and a bridge that relays presence would show Twalk's own machinery as the user. It **refuses to start** when the token's `whoami` is not `SENSOR_OWNER`: a device of somebody else's account joining portal rooms is a defect whose first symptom is a contact receiving a reply from a stranger. It **bootstraps no cross-signing and holds no recovery key** (`EncryptionSettings::default()`, the opposite of the Sensor's own): all four configured bridges carry `verification_levels.send: unverified`, so an unverified device is relayed like any other, and cross-signing is what a device needs to *read* history, which this one never does. And when a reply targets a **portal** room the device has not joined, nothing is posted at all — a transient failure, retried and then dead-lettered — because posting as `@sensor:` there returns an event id and reaches nobody, which #123 calls the worst possible answer; a room **no bridge marked** still goes out as `@sensor:`, since native Matrix traffic (ADR 0009) has no bridge to ignore it. That distinction is #216's half and it is on the bus: every successful post republishes the approval **unchanged** on `twalk.persona.reply.approved.v1.posted` with `reach` (`contact`/`nobody`) and `posted-as` headers — a sibling of the dead-letter subject, chosen because every v1 schema is `additionalProperties: false` and there is no type for "a reply was posted", so no contract had to grow a field — published on the good case as well as the bad one, because a signal that exists only when something failed makes success a silence. `twalk_sensor_outbound_replies_total{reach}` and `twalk_sensor_owner_device_rooms` (rendered **only** when a device is configured, so an absent sample is not a device in no rooms) are its half of `/metrics`. `sensor/tests/owner_device.rs` asserts it from the homeserver and the bus: the portal joined and the impostor room — built by a stranger who wrote a WhatsApp `m.bridge` marker into it — left at `invite`; the reply posted by the owner's account and by no other; and, in an **encrypted** portal, the reply written by a device that runs no message sync being **decrypted by a different device entirely** (the Sensor's own, which then publishes it as `outbound.message.sent`), since nothing else proves the room key was really shared. `sensor/tests/owner_is_never_a_contact.rs` reads the contract directory and fails on any type whose `subject` is a Matrix user ID and which has no recorded answer to "what happens when that person is the owner?", so an eleventh type cannot be added without the question being asked. Since ticket #174 the Sensor also **owns the bus's retention policy** (`bus`, ADR 0037): the `twalk` stream — which holds contacts' messages in cleartext, so the policy is a personal-data decision before a disk one — keeps ninety days and two GiB, the oldest discarded first, `s2`-compressed, with a **day** of `Nats-Msg-Id` tracking where NATS's two-minute default let a restart's re-sync reach every consumer twice; every field is named in one place, the three values are the operator's (`SENSOR_BUS_MAX_AGE_DAYS`, `SENSOR_BUS_MAX_BYTES`, `SENSOR_BUS_DUPLICATE_WINDOW_SECONDS`, a "no limit" value refused at startup by name), an existing stream is **updated in place** with each changed field logged `old → new`, a refused update is an `error` naming the field and the operator's options while the Sensor runs on the existing policy, and Twalk never deletes or recreates the stream (`tests/bus_policy.rs`, on the bus's own `STREAM.INFO`)
- `consent-cache/` — the `twalk-consent-cache` Cargo package (#273): the pure half of deciding consent, shared by every component that labels a sender — the cache keyed on `(subject, connection)`, the decision from the Gateway's snapshot plus the `consent.state.changed` stream, the refusal of an entry that names no connection, the exclusion of the owner's identities (`owner`) and the bridges' bots (`bridge_bot`), and the precedence between a contact's own decision and the connection's default. A path dependency of `sensor/` (which keeps only the I/O in `src/consent.rs` and re-exports `owner` and `bridge_bot` under the paths it always used) and, from lot 3 of #251, of the mail collector, so the two cannot disagree. Its unit tests are the ones that moved out of the Sensor; no Docker.
- `tests/harness/` — the `twalk-test-harness` Cargo package, shared by every component's suite: the test stack's lifecycle (`compose.test.yaml`, Synapse config, bot provisioning), the `Bus`, contract validation, `poll_until`, and a stub OpenAI-compatible LLM for persona tests. A dev dependency of `sensor/` and `hermes/`
- `hermes/` — the `twalk-hermes` Cargo package, in two halves. The **runtime** (ticket #23) is `src/`: it reads its persona list from the environment (`HERMES_PERSONAS`, a JSON array of an id and an argv), starts one process per persona, restarts a crashed one with exponential backoff, follows `consent.state.changed` from the beginning of the stream to learn which personas the user activated, and stops cleanly on SIGTERM — every transition a structured log, and no telemetry of its own, because observability is OTLP and opt-in (ADR 0017). Three of its decisions are load-bearing and each lives in its own module. `environment` **constructs** a persona's environment rather than letting it inherit the runtime's: the Companion Gateway's service token also opens the consent snapshot — the list of every contact — and a persona has no business holding that to learn which model to call (ADR 0015), and a third-party persona takes the same path as a first-party one (ADR 0008), so the control is that the variable is not there. `activation` moves a **consumer**, never a process: a paused persona still runs and receives nothing (ADR 0013), which the runtime renders as the filter subject of the durable consumer it owns — the inbound subject when active, `<prefix>.hermes.paused.<persona id>` (which nothing ever publishes on) when paused; `supervisor` cannot see the activation state at all, which is how that stays true. Per-network scoping is *not* enforced at the bus, because a subject carries no network. `supervisor` separates a crash from a persona that never started: a run shorter than `HERMES_PERSONA_HEALTHY_AFTER_MS` does not count, and `HERMES_PERSONA_START_FAILURES` of those in a row is announced once as `persona failed to start`, so a runtime that cannot start something is never indistinguishable from one that is still starting it. A persona that cannot reason fails five ways and each has its own message: no model configured is the runtime's refusal to start, unreachable-endpoint versus refused-request are the SDK's client in the persona's log, and since #162 a model that answered nothing and a model that spent its whole budget reasoning are two more — the last refused rather than retried. `environment` also carries `HERMES_USER_LANGUAGE` as `TWALK_USER_LANGUAGE` since #164, one line in the closed list, which is what gives ADR 0016's fallback a value to fall back to; a tag outside the Companion's five is refused at startup here, because injected it would be refused by every persona, on its first line, at every spawn. Ticket #184 built the span neither #98 nor #164 was asked for, and it is the fourth module: `settings` **reads the Companion Gateway** (`GET /api/settings/runtime`, `HERMES_GATEWAY_URL` and `HERMES_GATEWAY_SERVICE_TOKEN`, the same token that opens the consent snapshot), so the model and the language the user set in the browser are what the personas run with — before this, both halves of the bridge existed and `twalk-hermes` had no HTTP client at all, so a preference reached a persona only if an operator *also* typed it into `.env`, and somebody who changed their language saw the Companion confirm it and nothing happen. Four decisions in it are the ones to argue with. It reads **once, at startup**, because a persona's environment is built at spawn and re-applying a preference would mean restarting every persona — and the runtime therefore *says* at startup that a later change needs a restart, because a restart-to-apply nobody is told about is the same silent trap in a new place. An **unreachable Gateway does not stop the runtime**: the Sensor's answer to the identical question, copied rather than reinvented — start anyway, `ERROR` naming the URL *and what it fell back to*, retry in the background — with the corollary that a deployment nobody has named a model for runs and hosts nothing (ADR 0013's "allowed to exist, handed nothing") and starts its personas the moment one is named, with no restart, because **the retry exists to end an outage and never to apply a preference**. **Precedence is ADR 0015's generalised rather than a second decision**: a credential supplied as a file wins over one set from the browser, `.env` is the operator's other host-side voice, so the host wins **field by field** and the Gateway fills in the blanks, identically for the model and for the language — and that does not make the browser's value inert, because `.env.example` ships every one of those variables empty, so on the reference deployment the value in force is the Companion's and the startup line names each field's source. And **a persona's environment gains no new credential**: what crosses `environment`'s closed list is the *answer*, never the token that fetched it, which `tests/runtime_settings.rs` asserts on the container Docker really started in the run where the token was really used — and a language outside the five or a half-named model served by the Gateway is dropped with a reason rather than injected or fatal, because a stored row an operator cannot edit from a crash loop must not stop a deployment, while the same tag typed into `.env` stays a startup refusal. The one case only the runtime can see is an endpoint on **this host's loopback** — a perfectly good address (the reference deployment publishes a LiteLLM proxy there) that a persona in a container of its own network namespace dials as itself — so it warns at startup and names the fixes; making that address reachable is the deployment's job, not the runtime's, and `deploy/docker-compose/` answers it since ticket #158 by putting the runtime and its personas in the host's network namespace (ADR 0023). `hermes/README.md` holds every environment variable, including `HERMES_LLM_API_KEY_FILE`, which **wins** over `HERMES_LLM_API_KEY` so a production stack can lock the credential down (ADR 0015) — on a real deployment the model name comes from the browser and the key from a file, so that is the ordinary combination rather than the exotic one. Ticket #206 added four names to `environment`'s closed list — the seam to Hermes (`HERMES_WEBHOOK_URL`, `HERMES_WEBHOOK_SECRET` and two options), injected as `TWALK_HERMES_*` — and the second of them is the first **credential** that list has carried besides the model endpoint's key, which is worth stating rather than passing over: the rule the module keeps is not "a persona holds no secret" but that a persona holds no secret belonging to the *runtime*, and above all not the Gateway's service token, which opens the consent snapshot. A URL with no secret is a startup refusal (every persona would refuse it on its first line at every spawn); a secret with no URL is not, because the URL is what turns the seam on. The **persona** half is `personas/assistant/`, the reference persona (ticket #21): a container image built on the Python SDK that consumes `inbound.message.received` and publishes `persona.thinking.emitted` then `persona.suggest.produced`, with the consent gate, the deterministic ids and the headers all coming from the SDK. Integration tests in `hermes/tests/`: `smoke.rs` exercises the shared harness against the real stack, `suggestion.rs` is the suggestion policy (ticket #22) — every suggestion carries an `expires_at` one operator-set window (`TWALK_SUGGESTION_TTL_SECONDS`, an hour by default) after it was *produced*, not after its trigger, and a trigger the bus redelivers stays one suggestion at attempt 1 — and `assistant.rs` is the spec's seam 1 — the real persona **container**, driven by publishing contract fixtures to the bus with the stub LLM behind it, asserting the two events' schema validity, ids, headers and continued trace, and asserting the consent gate by the absence of both events and of any LLM call. `runtime_lifecycle.rs` is seam 2 — the real `twalk-hermes` binary starting the real persona image, asserting the three acceptance criteria and three absences (a paused persona receives nothing while still running; a persona's container environment holds none of the runtime's credentials; a persona whose image will not run is announced as failed) — `reasoning_budget.rs` is #162 at the persona's process boundary (the stub serves the reasoning-exhausted answer; the persona is asked **once**, the refusal names the budget and the remedy, and the bus's own account of the consumer shows nothing pending, awaiting an ack or redelivered — beside the contrast case, a model that said nothing, which *is* retried to the consumer's limit and says so), and `language_fallback.rs` is #164's (an ambiguous message with the preference set, asserting the prompt the stub was sent: the message's own language first, the user's language named once and only as the fallback — while `assistant.rs`, which configures no preference, asserts the absence, that no language is named at all and that the persona warns at startup), `hermes_seam.rs` is #206's — the real persona container against a stub of Hermes's webhook route (`tests/harness/hermes.rs`, which verifies the V2 signature the way the real adapter does, because a stub that accepted anything would let a persona sign nothing and still pass), asserting the body field by field against the bytes on the socket and every withheld identity's absence from them, that the consent gate lets nothing reach Hermes — not even a *refused* request, since one turned away at the door is one that was made — that the persona publishes `thinking` and no suggestion of its own and calls no model, that a redelivery is one wake under one key, and that a Hermes that is not there does not stop the persona — and `runtime_settings.rs` is #184's, over a stub Companion Gateway in `tests/harness/gateway.rs` (ports 17500–17699, 17699 reserved as the address of a Gateway that is not there): its decisive test **removes** `HERMES_LLM_BASE_URL`, `HERMES_LLM_MODEL`, `HERMES_LLM_API_KEY`, `HERMES_LLM_PARAMS` and `HERMES_USER_LANGUAGE` from the runtime's own environment — "nothing written into `.env`" — and asserts the language the Gateway holds in the prompt the stub LLM was really sent, the model in the same request, the credential in its `Authorization` header, the Gateway's service token nowhere in the persona The Hermes-specific half of the harness is `hermes/tests/harness/`: `PersonaRun`, which runs the persona image under its own compose project on a bus namespace of its own run (the persona container uses host networking, so it reaches the stack's published NATS port and the in-process stub LLM on loopback), and `RuntimeRun`, which runs the runtime and lets *it* start the persona — through `tests/run-persona-image.sh`, the argv the runtime is configured with in tests, which runs the image with whatever environment the runtime gave it and forwards every variable, so that an assertion about what a persona does not hold is worth making
- `sdk/python/` — `twalk_sdk`, the Python persona SDK (ticket #21), and the reason a persona author cannot breach consent by forgetting: **the consent gate lives in the SDK** (`consent.py`, applied before the author's handler and before the LLM client is touched, deciding on the envelope's `consent` extension alone so it never depends on a body a reduced event does not have — ADR 0012), alongside the contract's `persona.*` envelopes and their deterministic ids (`envelope.py`, whose output reproduces the contract's own fixtures), the durable pull consumer, the publishing with `Nats-Msg-Id` and the duplicated `network`/`consent`/`traceparent` headers, the suggestion policy (`policy.py`, ticket #22: the expiry every suggestion carries, and the attempt that counts suggestions rather than deliveries), the process loop (`persona.py`) and an OpenAI-compatible chat-completions client (`llm.py`). No default LLM (ADR 0015): a persona refuses to start without the endpoint *and* the model the operator named, and `TWALK_LLM_PARAMS` is a JSON object of provider parameters merged into every request untouched — a parameter set to `null` removes a field the request would otherwise carry, which is how a provider that rejects one is made to work; in a deployment that configuration comes from the Gateway and is injected by the runtime (#23). Since #162 the answer a model gives is read by `completion.py`, pure and stdlib-only, which names **four** outcomes where there was one: unreachable, refused, answered nothing, and **spent its whole budget reasoning** — `HTTP 200`, `finish_reason: "length"`, `content: null`, the budget in `reasoning_content`, which is what the reference deployment's Qwen answered to every message and what the persona used to report as "the chat-completions answer carries no content" while retrying for ever. That one is the only one marked non-transient, and the loop reads exactly that: it **terminates** the delivery on the first try, with a refusal naming the budget and `HERMES_LLM_PARAMS`, because the same request gets the same non-answer and each one is billed — and a retried outcome that reaches the consumer's redelivery limit now says so instead of letting the trigger disappear, so neither kind is left apparently unprocessed. Since #164 the SDK also **names** ADR 0016's fallback: `TWALK_USER_LANGUAGE` (`language.py`, a closed list of the Companion's five, refused at startup otherwise) is the language a persona writes in when it cannot tell what language the message it answers was written in, and nothing else. Unset is a supported state and is stated rather than chosen silently — a warning at startup naming the variable and where it is set — because refusing to start over an ambiguous case would stop a deployment that answers every readable message correctly. Ticket #206 added the first thing in this project that speaks to something **outside** the deployment, and it is two modules split the way `completion.py` and `llm.py` are: `webhook.py` is pure and decides what crosses — a **narrow template of ten named fields**, never the raw event, because Hermes keeps memories and nothing expires what it is shown, so a body copied into `MEMORY.md` outlives ADR 0028's seven days on a machine Twalk may not own — and `hermes.py` owns the socket. What the template withholds is the point and is asserted as such (`tests/test_webhook.py` pins the whole key set with `==`, then searches the serialised body for the sender's Matrix ID, the display name, the `network_identifier`, the portal room, the quoted excerpt and the attachment's decryption material): a persona author cannot widen it, for the same reason they cannot forget the consent gate. Three more decisions are in it. The signature is Hermes's **generic V2** — hex HMAC-SHA256 of `<timestamp>.<body>` — because V1 signs the body alone and a captured request replays for ever. The idempotency key is the **suggestion's own deterministic id**, which is also `Nats-Msg-Id` on the bus, so Hermes's hour-long delivery cache and the bus's deduplication cannot disagree and a redelivered trigger is neither a second agent run nor a second draft. And **TLS is required by configuration**: an `http://` URL is a startup refusal unless `TWALK_HERMES_ALLOW_INSECURE_URL` records that somebody accepted the hop, which is then warned about on every start — the HMAC authenticates the sender and not the content, so plaintext gives the message no confidentiality at all. An unreachable Hermes does not stop the persona (the Sensor's shape for the consent snapshot, copied: start anyway, `ERROR` naming the URL, re-probe in the background), and a route over its rate limit is its own transient failure with a delay of its own, because Hermes's 30-a-minute default and ADR 0013's "a fresh consumer starts at the beginning of the stream" are in direct conflict on a replay. Packaged as a container image, never installed on a host (no pip — PEP 668 — and no venv module). Its pure half is stdlib-only and unit-tested in place against the contract's fixtures (`sdk/python/tests/`, `python3 -m unittest discover -s tests`); `Persona` and `Llm` are imported lazily, which is what keeps that possible. `sdk/python/README.md` holds the decisions and every environment variable

Fifteen rather than the original five is #186, and the number is the suite's **tolerance** rather than a preference: the client renews with a fifth of the lifetime in hand (`refreshAfterSeconds`), so the absolute headroom these specs have is a fifth of whatever this origin configures, and at five seconds that was one — less than a browser timer slips on a machine that is linking a Rust binary, so the suite lost to load it created itself and was reported as flaky. Three things went with it, each a case of the suite measuring itself rather than the product: the `session` project was ordered last and then deliberately left unordered again — measured, it passes on a host pinned at load 25–30, so it does not need an idle machine, and a `dependencies` chain would silence the one suite that proves an expired session is refused whenever an earlier project went red; the death of a credential is asked of the Gateway rather than slept for, because the page rotates its token when it likes and "a lifetime from now" was never a bound on when the one it holds dies; and this project has a **stated test budget** (`journeyBudgetMs`) instead of the default thirty seconds, which was quietly carrying an eighteen-second deliberate wait plus a real-stack journey. Since #185 the suite also refuses to adopt a server it did not start: `tests/build-id.mjs` names a build by hashing the export, `tests/serve-like-gateway.mjs` publishes the name it serves at `/__twalk_test__/serving`, and `tests/port-guard.mjs` — run from `playwright.config.ts`'s own body, because `webServer` starts before `globalSetup` — either adopts a server that proves it is serving this build, or stops the run naming the port, the pid, the command, when it started and which build it serves (`tests/e2e/ports.spec.ts` asserts that diagnosis and needs no stack). It also reaps itself: a `serve-like-gateway.mjs` exits on `SIGINT`/`SIGTERM`/`SIGHUP` and when the run that started it is gone, because one left on port 4319 for twenty-eight hours made the suite test a day-old build and fail thirty-six tests as though the code were broken. `companion/README.md` holds the decisions
- `clerk/` — the `twalk-clerk` Cargo package, the **clerk** (*le greffier*, ticket #265): the fifth component, and the one that writes onto the owner's Buzz relay what the bus says. It consumes the bus with durable consumers and writes into the three channels `provision-buzz-channels.sh` created for it — one forum post per `persona.suggest.produced` in `approbations` (the suggestion's body verbatim, the clerk's own sentences and a reference line, and **nothing else**: no display name, no excerpt, no `network_identifier`, no room id, because the approval screen cannot name the contact and this surface cannot either, #160, ADR 0012), one line per `twalk.persona.reply.approved.v1.posted` in `journal` (what went out, on which network, posted as which account, `reach` — `contact` visibly not `nobody` — and **no text**, so "nothing Twalk writes onto Buzz quotes a contact" stays true without an exception to defend), and in `activite` only what calls for a look — a bridge down and back, a consent decision, a suggestion produced, a suggestion that expired undecided — and never `persona.thinking.emitted`, a message count or a sender identity, since on Buzz a channel that chatters is a channel that gets muted. Three decisions in it are the ones to argue with. It signs with **a Nostr key of its own** (`CLERK_NOSTR_KEY_FILE`; `provision-nostr-key.sh` generates one, and the owner tells the relay to accept it and adds it to each channel with `provision-buzz-channels.sh --bot`): not Hermes's, because the reader must know who speaks and what Twalk decided about consent and delivery is not Hermes's to say, and not the Gateway's, because ADR 0032 refuses a Nostr private key in the Gateway — and the clerk holds no credential the Gateway would take for anyone but the owner's own device: not the service token that opens the consent snapshot, and no device token at rest beyond the fifteen minutes one lives in memory. It **holds no state** (ADR 0035): what it already posted it finds by reading its own posts and the key each carries — the reference line on a forum post, an `r` tag naming the bus event on a `journal` or `activite` line — so a redelivery and a restart are the same read, and a SQLite of suggestion id → post id was weighed and rejected because a store makes the relay a copy of something Twalk holds. And the **sweep** (`CLERK_SWEEP_SECONDS`, a minute by default) deletes a suggestion's post the moment it expires (#219) and says so in `activite`, so the relay never holds a quoted word longer than a suggestion lives, well inside ADR 0028's seven days. An unreachable relay costs a warning, a counter and a retry with backoff, never the process, and a suggestion that expired meanwhile is skipped and counted rather than posted stale. `CLERK_RELAY_URL` is the URL the relay **announces**, because a Buzz relay is multi-tenant by `Host`; `CLERK_USER_LANGUAGE` is one of the Companion's five, refused at startup otherwise. Ticket #284 gave it its **write half** (ADR 0036), and the decision in it is the one to argue with: a **✅ by the owner** on a post in `approbations` is **the** approval — the Companion Gateway's, through `POST /api/approvals`, the call the approval screen makes — a reply in the thread approves with that text (the edit #100 allows), a ❌ deletes the post locally and reaches nothing, and the clerk makes the call **as a device of the owner** named `Buzz`: signed in once by an operator route (`deploy/docker-compose/provision-clerk-device.sh` — the owner's Matrix password at the terminal, a Matrix OpenID token, `POST /api/session`, the refresh token written into a host directory `CLERK_GATEWAY_SESSION_DIR` at 0600), listed on the dashboard and revoked there like a phone, kept alive by `POST /api/session/refresh` with the refresh token rotated **on disk before the new device token is believed** (`gateway.rs`), so the approval row reads `approved_by: <owner>` through that device. Not a second service token (a second class of credential, `approved_by` fixed by configuration, nothing on the dashboard to revoke) and not NIP-98 on the Gateway (a Nostr verifier on the write path for one client, and a second identity for the owner beside the Matrix one). **Who may** is the owner's Nostr key alone, `CLERK_OWNER_PUBKEY`, from configuration and never read off the relay — a relay `admin` is not the owner — and a gesture by any other key makes no Gateway call, is answered once in the thread and is counted. The **refusal vocabulary is the Gateway's**: every code is answered in the thread with the Companion's own sentence for it, embedded from `companion/src/lib/i18n/{fr,en}.json` at build time (`refusals.rs`, which is why `clerk.Dockerfile` copies that directory into the context and why `companion/src/lib/i18n/` and `companion-gateway/openapi.yaml` trigger the clerk's suite), in `CLERK_USER_LANGUAGE`, and checked both ways against `openapi.yaml` the way `refusal.test.ts` does; `already_approved` is success; a `401` on a session the Gateway will not have is answered once naming the dashboard and the script, never retried. The reaction is the retry: a ✅ present at startup is carried, a redelivery sends once (an approved post is gone; an answered gesture carries its id in an `r` tag — ADR 0035 unchanged, since the session file is a credential and not state), and an unreachable Gateway is retried for the suggestion's remaining life and then said. The compose service sets the three write-half variables only together (`${VAR:+…}`), mounts the session **directory** and never the file (the rewrite is a rename), and `clerk/src/config.rs`'s compose guard reads that block and fails on any variable that names a credential. `/health` and `/metrics` (`twalk_clerk_posts_total{channel}`, `twalk_clerk_deleted_total{why}`, `twalk_clerk_skipped_total{why}`, `twalk_clerk_approvals_total{outcome}` — six fixed outcomes plus the Gateway's codes as they occur) are its origin. Integration tests in `clerk/tests/` run against a **real Buzz relay** the suite brings up itself beside the shared Synapse/NATS stack, under its own compose project (`TWALK_CLERK_TEST_STACK`, `twalk-clerk-test` by default) and port (`TWALK_CLERK_TEST_RELAY_PORT`, 17800): `smoke.rs`, `approbations.rs` (one post per suggestion across a redelivery and a restart, and a trigger whose body, excerpt, display name and `network_identifier` are distinctive markers searched for in every event of every channel), `journal.rs`, `activite.rs`, `sweep.rs` and `decisions.rs` (#284, over a stub Companion Gateway in `tests/harness/gateway.rs`, ports 17400–17499, since the real one needs a Synapse owner and belongs to the deployment suite) and `deployment.rs` (advisory, `TWALK_CLERK_DEPLOY_TEST_*`, ports 18380–18383: the deployed Companion Gateway, the clerk's own compose service and the real `provision-clerk-device.sh` — one row in the real approval table through the device `Buzz`, a container environment inspected for credentials, and a device revoked from the dashboard restored by the script under `sudo`, which the runner therefore needs passwordless). `clerk/README.md` holds every environment variable and the decisions
- Other component directories hold stub READMEs only: `ui/`, `examples/`, `tools/`

## Build and test commands

Run these to find out whether your change works. They are not the verification — a pull request gets its verdict from the `verified` check (see "Continuous integration" below), and "I ran the suites in my worktree" is evidence for a reviewer rather than a substitute for it. Two red-`main` incidents came from a shared change merged on the strength of exactly that sentence.

Requires Docker (the harness brings up its own Synapse + NATS stack) and a Rust toolchain.

Five Cargo packages, each with its own lockfile and target directory — there is no workspace, so build and test each from its own directory:

```bash
cd sensor
cargo build --tests   # compile / typecheck
cargo test            # full suite: boots the stack itself, ~15s cold, ~3s warm

cd ../hermes
cargo test            # Hermes suite: shares the same test stack, and builds the persona image itself

cd ../companion-gateway
cargo test            # Gateway suite: the binary at its process boundary, plus its compose service

cd ../clerk
cargo test            # clerk suite: the binary against a real Buzz relay the suite brings up itself

cd ../tests/harness
cargo test            # the shared harness's own unit tests (no Docker)

cd ../../consent-cache
cargo test            # the shared consent cache's own unit tests (no Docker)
```

The Python SDK's pure half — the consent gate, the envelopes, the configuration — is stdlib-only, so its unit tests need neither pip nor Docker (there is no pip on the host, by design: personas ship as images):

```bash
cd sdk/python
python3 -m unittest discover -s tests   # the gate, the deterministic ids, the envelopes
```

The Companion is the one non-Cargo component: Node 22 and npm, from `companion/`.

```bash
cd companion
npm ci                # install; runs `svelte-kit sync`
npm test              # api:check + svelte-check + Vitest + build + Playwright
npm run test:e2e:stack  # the same Playwright suite with a real Gateway and Synapse behind /api
npx playwright install chromium   # once, before the first `npm run test:e2e`
```

`npm test` needs neither Docker nor Rust: the bootstrap journey
(`tests/e2e/bootstrap.spec.ts`) skips itself with a reason. `npm run
test:e2e:stack` is the one that runs it, bringing up the shared test stack and
building the Gateway binary (`TWALK_TEST_STACK`, `TWALK_TEST_SYNAPSE_PORT`,
`TWALK_TEST_NATS_PORT` move the stack aside; `TWALK_TEST_PORT` moves the
Companion's own origin, which matters when another worktree is running its
suite).

**What the Companion's real-stack suite needs of a host, and how to read a red run** (#148). One run starts three Gateways, a Synapse, a bus, two stub bridges and — by default — ten browsers at once, so it is the load it fails under. Measured on the reference host (20 cores, memory- and I/O-bound, running the deployment beside the suite): every flake in six full runs was `element(s) not found` after Playwright's five-second `expect` on a locator the page renders on boot, in a `chromium` test that passed in under a second alone or in a `--project=chromium` run without the stack; the `networks` project alone passed 4/4 on load 5–9. Three things follow. The `expect` timeout is **fifteen seconds with the stack** and the `chromium` project runs **four workers** there (`playwright.config.ts` says why, with the numbers); both are tolerances, and neither changes which answer is wrong. **Do not run two real-stack suites at once on one host**: the `consent` and `portals` projects each start a real Sensor whose consent consumer is a durable with a constant name, so two runs split the consent stream between them — and two worktrees running `npm test` (no stack) at once are fine, given distinct `TWALK_TEST_PORT`s. And a summary that says **"N did not run"** is neither green nor red about the code under change: the real-stack projects are chained (`networks` → `dashboard` → `approvals` → `consent` → `portals`) because they share one Gateway, one consent journal and one login per bridge, so a red journey in one stops everything behind it; `tests/did-not-run-reporter.mjs` prints which project failed and which tests it kept from running, so a reader looks there rather than at the diff.

`npm run api:check` is the one to remember when working on the Gateway: it fails when `companion/src/lib/api/` no longer matches `companion-gateway/openapi.yaml`, and `npm run api:generate` in `companion/` is the fix.

The Sensor and Hermes suites bring up the same test stack (one Synapse, one NATS JetStream), each on its own bus subjects; `TWALK_TEST_STACK`, `TWALK_TEST_SYNAPSE_PORT` and `TWALK_TEST_NATS_PORT` move a stack aside for a parallel worktree. The Hermes persona tests take that further, because a durable consumer over the shared `twalk.>` history would replay every message another suite ever published: each gives the persona a JetStream stream and a bus subject prefix of its own run (`TWALK_BUS_SUBJECT_PREFIX`, `twalk` in every deployment), and deletes the stream and the container when it is done. The Companion Gateway's suite uses the same stack: real Synapse mints the OpenID tokens its sign-in tests need and answers the admin registration call bootstrap relays (the test Synapse serves the `openid` resource for the first), and its consent tests publish to the same NATS JetStream, reading back the events they caused by the ids the write API returned. Its process-boundary tests ask the kernel for a free port, and its pending-contact suite publishes contract-valid inbound events onto the same JetStream and reads the list back over HTTP; its deployment test uses the deploy-stack variables (`TWALK_DEPLOY_TEST_STACK`, `TWALK_DEPLOY_TEST_GATEWAY_PORT`, `TWALK_DEPLOY_TEST_SYNAPSE_PORT`, `TWALK_DEPLOY_TEST_NATS_PORT`) the Sensor's deployment test established — its bootstrap test is the one that needs the bus, since it asserts the invited room's traffic on it. `sensor/tests/bridges_deployment.rs` runs the reference deployment a third time, with the `bridges` profile on and all three bridges up, under its own `TWALK_BRIDGES_TEST_*` project, ports and teardown flag; since #172 it also runs it a fourth way, with **no** bridge variable set at all (`TWALK_NO_BRIDGES_TEST_*`, torn down every run), because a stack that runs no bridge must never be asked for a bridge token — its module docs list them. `companion-gateway/tests/portals_deployment.rs` runs it again on a stack of its own (`TWALK_PORTALS_TEST_STACK`, ports 17309/17319/17329, `TWALK_PORTALS_TEST_KEEP=1` to keep it): the whole deployment comes up first, a portal room is built afterwards, the user chooses it, the **real Sensor** joins on the bridge bot's invitation and the conversation reaches the bus — and it tears its stack and its per-stack images down at the end of every run, passing or failing. `hermes/tests/full_loop.rs` runs it a fourth time, because the full loop needs a real Sensor to post the approved reply, a real Gateway to serve the approval and — since #158 — the deployment's own Hermes to produce the suggestion: its own `TWALK_LOOP_TEST_STACK` project and ports 19508/19518/19522 (`TWALK_LOOP_TEST_SYNAPSE_PORT`, `TWALK_LOOP_TEST_GATEWAY_PORT`, `TWALK_LOOP_TEST_NATS_PORT`), and — unlike the other three — it tears its stack and its per-stack images down at the end of every run, passing or failing (`TWALK_LOOP_TEST_KEEP=1` keeps them).

## Continuous integration

A pull request is verified by `.github/workflows/pull-request.yml`, and three checks decide it: **`routing`** (the routing table against the repository), **`verified`** (every selected suite that needs no Docker) and **`verified-stack`** (every selected suite that does — red until `vars.TWALK_STACK_RUNNER` names a runner, deliberately, so a green tick never means "those never ran"). Three things to know before reading a red one, with the rest in `docs/agents/continuous-integration.md`:

- **What runs is a function of what changed**, and it is decided by `.github/ci/suites.json` — never by a `paths:` filter in a workflow. A change to `contracts/`, `tests/harness/` or `companion-gateway/openapi.yaml` runs the **consumers'** suites, and `.github/ci/test_selection.py` derives those consumers from the repository's own dependency graph rather than trusting the table, so a fourth consumer of the harness fails the routing check until it is routed. Adding a suite, or a Rust test file, means editing that table; the same test fails if you do not.
- **The deployment suites are advisory.** `sensor-deployment`, `gateway-deployment`, `hermes-full-loop`, `clerk-deployment` and `companion-e2e-stack` do not block a merge: they run nightly on `main`, and on a pull request only when it carries the **`ci:deployment`** label. Add the label when you touch `deploy/docker-compose/` or `bridges/`.
- **No suite with an open flake ticket is in the required tier** (#148), and none is promoted while that ticket is open. So a red required check means something — do not re-run it until it passes. #186 closed the `session` project's races and #200 the `consent` project's failing spec, which is most of what stood in front of `companion-e2e-stack`; #148 is what is left, and its own criteria reach into `companion/src/lib/networks/` (a screen that reads its state once on mount shows a transient failure as a permanent one to a *user*, not only to a test).

The stack suites need a self-hosted runner, named by the repository variable `TWALK_STACK_RUNNER`. Until it is set they report that they did not run and print the command to type instead. Their ports and compose projects are all set in one place, `.github/ci/stack-env.sh`, in the 18300–18499 band, and `.github/ci/stack-teardown.sh` runs after every one of them, passing or failing.

## Code organization

Monorepo with 14 top-level directories — see the "Repository layout" section of `README.md`. Stacks: Rust for `sensor/`, `hermes/`, `companion-gateway/` and `clerk/`, SvelteKit (static export) for `companion/`, Python for `sdk/python/` and the personas in `hermes/personas/` (ADR 0008: the runtime is Rust, personas are separate processes and Python's LLM ergonomics stay inside them). The Sensor test harness speaks the Matrix client-server API over plain HTTP — the HTTP `Bot` helpers deliberately do not depend on matrix-sdk; the exception is the `CryptoBot` helper (`sensor/tests/harness/crypto.rs`), which runs matrix-sdk with its crypto stack because raw HTTP cannot Megolm-encrypt.

## Code style guidelines

**Do not run a formatter.** There is no Prettier, rustfmt-on-save or equivalent configured anywhere in this repository, and none is wanted: the style is tabs, single quotes and a ~100-column wrap in the TypeScript and Svelte, and `cargo fmt` defaults in the Rust, all maintained by attention. A `npx prettier --write` here resolves to whatever binary is on the machine, applies *its* defaults, and rewrites whole files — two merges once turned a 200-line change into 1560 insertions and 1464 deletions, which had to be undone by hand. Match the file you are editing. (`cargo fmt` is the one exception, and only because the Rust crates were written to it.)

In all naming and prose, follow the `CONTEXT.md` vocabulary: **network** (never "channel" outside user-facing copy, never a bridge name like `gmessages`), **persona** (never "bot" for agent identities — test Matrix users standing in for bridges are "test bots"), **the Companion** means the PWA only, **Companion Gateway** always in full.

## Testing instructions

Tests live at the agreed seam: the component's process boundary (real Synapse + real NATS JetStream). What every suite shares is in the `tests/harness/` crate (stack lifecycle, `Bus`, `validate_against_contract`, `poll_until`, the stub LLM); component-specific helpers stay with their component (`sensor/tests/harness/` and `hermes/tests/harness/` both re-export the crate, so each component's test files see one flat `harness::` namespace). For a persona the process boundary is a **container's**: `hermes/tests/harness/`'s `PersonaRun` brings up the image the persona ships as, and a test asserts only what appeared on the bus and what the stub LLM was sent. New test files go beside `smoke.rs`. Every event-producing behaviour must assert schema validity via `validate_against_contract`. Keep tests isolated from persisted stack state (unique rooms and bus subjects per run).

## Security considerations

Never commit secrets, credentials, or `.env` files (`.gitignore` covers `.env`). The only secrets in the repo are the throwaway constants in `tests/harness/synapse/homeserver.yaml` and the test-bot passwords — local, ephemeral test stack only; never reuse them elsewhere. Message content is highly sensitive by design: no message may leave the user's infrastructure without explicit consent — keep that invariant in mind for any code that touches event payloads.
